## 第一部分：测试选择

### 按项目实际能力选择

**不假设项目具备某类能力，也不为了"流程完整"引入测试框架。**

| 验证类型 | 作用 | 适用条件 |
| --- | --- | --- |
| Lint | 代码规范与常见错误 | 项目有 lint 配置与可执行脚本 |
| 类型检查 | 类型错误 | 项目使用静态类型且有类型检查脚本 |
| 单元测试 | 纯逻辑、工具函数、数据转换 | 项目有测试运行器与可执行脚本 |
| 组件测试 | 组件渲染与交互 | 项目有组件测试环境 |
| E2E | 完整业务流程 | 项目有 E2E 框架且可在当前环境运行 |
| 视觉对比 | 与设计稿或基线的视觉差异 | 项目有视觉回归能力，或有 UI 图可人工对比 |
| 构建 | 产物能否正常生成 | 项目有构建脚本 |
| 浏览器 / 真机 / 平台验证 | 真实运行环境下的行为 | 有对应设备或平台环境 |

### 如何判断项目具备哪些能力

**从项目脚本与配置识别，不假设命令名。** 同名脚本在不同项目里做的事可能完全不同，所以要读脚本的实际内容。

| # | 步骤 | 看什么 | 得到什么 |
| --- | --- | --- | --- |
| 1 | 读包描述文件的脚本字段 | 全部脚本的名称与**实际命令内容** | 可执行命令清单及各自实际做什么 |
| 2 | 读 CI 配置 | CI 里实际跑了哪几条命令、顺序、失败判定 | 团队认可的验证组合（比脚本清单更可信） |
| 3 | 读各类工具配置文件 | lint / 格式化 / 类型 / 测试 / E2E 的配置是否存在且非空 | 能力是否真正配置好 |
| 4 | 搜测试文件 | 是否存在测试文件、放在哪、命名约定、数量 | 测试能力是否真在使用（有配置无测试的情况很常见） |
| 5 | 读项目规范文档 | 提交前要求跑什么 | 团队约定的最低验证标准 |
| 6 | 先做一次无副作用的试运行 | 命令能否正常启动 | 排除"脚本存在但环境缺依赖跑不起来"的情况 |

**判定规则：**

| 判定 | 条件 |
| --- | --- |
| 具备该能力 | 脚本存在 + 配置存在 + 能实际跑起来 |
| 形式上有但不可用 | 脚本存在但配置缺失、依赖缺失或直接报错 |
| 不具备 | 没有对应脚本与配置 |

"形式上有但不可用"要按"不具备"处理，并在 `delivery.md` 说明原因（例如需要安装依赖——而安装依赖需要单独授权）。

### 项目缺少某类能力时

**不强行引入测试框架。** 引入测试框架属于新增依赖 + 扩大范围，需要单独授权，且会显著改变本次交付的性质。

正确做法：记录替代验证方式与未覆盖风险。

| 缺少的能力 | 替代验证方式 | 未覆盖风险的表述方式 |
| --- | --- | --- |
| 单元测试 | 手动构造边界输入验证关键逻辑；在 `delivery.md` 记录输入与结果 | 逻辑改动无自动回归保护，后续修改可能引入回归 |
| 组件测试 | 手动在浏览器/真机操作组件的各状态 | 组件状态切换无自动验证，依赖人工执行 |
| E2E | 手动执行完整流程并记录每步结果 | 流程回归需人工执行，改动后可能遗漏 |
| 视觉回归 | 目标屏幕下人工对比 UI 图 | 细微像素差异可能遗漏 |
| 类型检查 | 依靠 lint 与人工核对数据结构使用 | 类型错误只能在运行时发现 |

**表述要求：** 未覆盖风险要具体到"哪部分逻辑没有自动保护、什么情况下会出问题"，不要写成"测试覆盖不足"这类无信息量的话。

**例外：** `plan.md` 里已经批准了"补充测试"任务且项目具备测试能力时，按计划补测试——这不属于引入框架。

## 第二部分：覆盖范围

至少覆盖以下与本次需求相关的方面。**与本次需求无关的部分不需要覆盖**（不需要为一个页面改动去回归整个应用）。

| # | 覆盖项 | 要验证什么 | 常见遗漏 |
| --- | --- | --- | --- |
| 1 | 正常流程 | 主路径能走通，结果正确 | 只验证"页面能打开"，不验证结果数据正确 |
| 2 | 异常流程 | 请求失败、校验失败、权限不足时的表现 | 只测成功路径 |
| 3 | 重复操作 | 连续快速点击、重复提交、重复触发 | 完全不测，上线后出现重复数据 |
| 4 | 网络问题 | 慢网、断网、超时、请求中途离开页面 | 只在快网下测试 |
| 5 | 加载与空状态 | 加载态是否出现、空数据态是否正确 | 测试数据总是非空，空态从未被看到 |
| 6 | 长文本 | 超长文字、超长列表、极值数字的布局表现 | 只用短的测试数据 |
| 7 | 目标屏幕 | 需求覆盖的屏幕尺寸下布局正常 | 只在开发机的一个尺寸下看 |
| 8 | 登录与权限 | 未登录、已登录、各角色、登录态失效的表现 | 只用一个高权限账号测 |
| 9 | 跨端跳转 | 跨端/跨项目跳转的参数传递与落地页表现 | 只测发起端，不测接收端 |
| 10 | 旧功能回归 | 受本次改动影响的既有功能行为不变 | 完全不做回归 |

### 回归范围怎么定

回归范围来自 `context.md` 复用分析里的**调用方清单**：

| 本次改动类型 | 回归范围 |
| --- | --- |
| 只新增文件，未修改现有文件 | 验证新功能 + 新功能的入口所在页面 |
| 修改了业务文件 | 该文件涉及的功能 |
| 修改了公共能力（请求、登录、权限、埋点、公共组件、公共工具） | **全部调用方**。调用方多时按重要性排序，至少覆盖核心链路 |
| 修改了路由或全局配置 | 受影响的全部页面入口 |

回归范围无法全部覆盖时，说明覆盖了哪些、未覆盖哪些、未覆盖的风险，由开发决定是否接受。

## 第三部分：证据要求

### 必须记录的五项

`delivery.md` 的验证证据必须包含：

| # | 记录项 | 要求 | 反例 |
| --- | --- | --- | --- |
| 1 | 执行的准确命令 | 完整命令 + 执行目录 + 所属项目 | "跑了 lint" |
| 2 | 结果 | 退出码或明确的成功/失败结论 | "没什么问题" |
| 3 | 失败数量 | 具体数字；失败项的摘要（文件 + 原因） | "有几个警告" |
| 4 | 未执行项及原因 | 哪项没执行、为什么（缺环境 / 缺账号 / 缺能力 / 需要授权） | 直接不提未执行的项 |
| 5 | 人工验证项 | 每项的操作、结果、执行人角色、执行时间 | "已人工验证" |

### 三种状态必须能区分

这是证据要求的核心。任何验证项都必须落到三种状态之一，**不允许含糊**：

| 状态 | 含义 | 记录要求 |
| --- | --- | --- |
| 通过 | 本次实际执行且达到通过标准 | 命令 + 结果 + 通过标准的对照 |
| 失败 | 本次实际执行但未达到通过标准 | 命令 + 失败数量 + 失败摘要 + 是本次引入还是既有问题 |
| 未执行 | 本次没有执行 | **必须写原因**，并说明未覆盖的风险 |

**"未执行"的常见原因（都要如实写）：**

- 项目不具备该能力
- 缺少测试账号、环境或数据
- 缺少设备或平台环境
- 需要授权才能执行（例如需要安装依赖）
- 依赖的前置验证未通过
- 需要人工执行但尚未执行

**证据表格形态：**

```markdown
### 自动验证

| # | 项目 | 命令 | 状态 | 结果 | 备注 |
| --- | --- | --- | --- | --- | --- |
| V1 | <项目名> | <实际执行的完整命令> | 通过 | 退出码 0，本次改动文件 0 error 0 warning | - |
| V2 | <项目名> | <实际执行的完整命令> | 通过 | 退出码 0，0 个类型错误 | - |
| V3 | <项目名> | <实际执行的完整命令> | 失败 | 退出码 1，2 个用例失败 | 均为既有问题，见下 |
| V4 | <项目名> | <实际执行的完整命令> | 未执行 | - | 依赖 V3 通过 |
| V5 | <项目名> | - | 未执行 | - | 项目无 E2E 能力，改为手动 M1~M4 |

执行时间：<日期时间>

### 失败明细

| # | 失败项 | 摘要 | 归属 | 处理 |
| --- | --- | --- | --- | --- |
| F1 | <测试文件>/<用例名> | <失败原因摘要> | 既有问题（改动前同样失败，已验证） | 记入遗留事项，未修复 |
| F2 | <测试文件>/<用例名> | <失败原因摘要> | 既有问题 | 同上 |

### 人工验证

| # | 验证项 | 操作 | 预期 | 实际 | 状态 | 执行角色 | 时间 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| M1 | 正常流程 | <步骤> | <预期> | <实际> | 通过 | 开发 | <时间> |
| M2 | 无权限 | <步骤> | <预期> | - | 未执行 | - | - |

M2 未执行原因：需要受限角色账号，尚未获得（账号由开发提供，不记录在本文件）。
```

### 不得声明全部完成

**硬约束：任何验证未执行或失败时，不得写"全部验证通过"或"交付完成"。**

| 实际情况 | 正确表述 | 错误表述 |
| --- | --- | --- |
| 4 项自动验证通过，2 项人工验证未执行 | "自动验证 4 项全部通过；人工验证 2 项待执行，清单见下" | "验证通过，可以交付" |
| 测试有 2 个既有失败 | "测试执行完成，2 个用例失败，均为既有问题（附证据），本次改动未引入新失败" | "测试通过" |
| 项目无 E2E 能力 | "项目不具备 E2E 能力，改用手动验证 M1~M4，未覆盖风险：<具体风险>" | 不提 E2E |
| 构建未跑（依赖前置项） | "构建未执行，原因：依赖 V3 通过" | 省略构建行 |

### 区分本次引入与既有问题

| 步骤 | 做法 |
| --- | --- |
| 1. 判断归属 | 在未包含本次改动的状态下执行同一命令，对比结果。差异部分是本次引入 |
| 2. 记录证据 | 既有问题要记录"改动前同样失败"的可复现证据，不能只是断言 |
| 3. 处理本次引入 | 修复后**重跑完整验证**（不是只跑失败的那一项） |
| 4. 处理既有问题 | **不擅自修复**，但必须报告 |

**为什么不擅自修复既有问题：**

1. 修复超出批准范围，扩大 diff。
2. 既有失败可能是团队已知并接受的，或者其他人正在处理。
3. 修复既有问题可能改变其他功能行为，回归成本不在本次评估范围内。

**必须报告的内容：** 失败项、可复现证据、与本次改动的关系（无关 / 相邻但无关）、未覆盖的风险、修复建议。开发明确接受该风险并写入 `decisions.md` 后才能继续交付，但**仍不得写成"全部验证通过"**。

**例外：** 既有问题导致本次功能无法验证时（例如既有的构建失败让构建验证无法执行），这属于阻塞，暂停询问开发是否授权修复，不自行决定。

## 第四部分：验证阶段的状态规则

这部分容易写错，逐条对照执行。

### 状态判定表

| 实际情况 | `stageStatus.verification` | 阻塞项 | `delivery.md` 要写什么 |
| --- | --- | --- | --- |
| 全部必要验证（含人工）通过并经开发确认 | `complete` | 无 | 完整证据 |
| 自动验证通过，人工验证项未执行 | **`awaiting_confirmation`** | 无 | **待人工执行清单** |
| 本次修改导致失败，已修复并重跑通过 | 按上面两行判断 | 修复后移除 | 记录失败与修复过程 |
| 本次修改导致失败，无法修复 | `blocked` | **`verification_failed`**，scope 为受影响模块 | 失败证据 + 影响范围 + 需要的支持 |
| 既有问题失败，开发已接受风险并入 `decisions.md` | 按人工验证是否完成判断（`complete` 或 `awaiting_confirmation`） | 无 | 失败证据 + 风险接受记录；**不写"全部通过"** |
| 验证正在进行 | `active` | 无 | 逐步补充 |

### 关键规则

**规则 1：人工验证未执行 → `awaiting_confirmation`，不是 `complete`。**

自动验证全绿不等于验证完成。人工验证项（登录、权限、真机、视觉、跨端）没执行时，验证阶段是 `awaiting_confirmation`，`delivery.md` 必须列出待人工执行清单：

```markdown
### 待开发人工执行的验证

| # | 验证项 | 操作步骤 | 预期结果 | 需要的条件 | 为什么 AI 无法执行 |
| --- | --- | --- | --- | --- | --- |
| M2 | 受限角色权限 | <步骤> | <预期> | 受限角色账号（由开发提供） | 无测试账号 |
| M5 | 真机视觉对比 | <步骤> | <预期> | 目标机型 | 无真机环境 |
```

清单要具体到可执行——开发照着做就能完成，不需要再回来问细节。

**规则 2：本次修改导致失败 → 修复后重跑完整验证。**

不是只重跑失败的那一项。修复可能影响其他项（例如为了让测试通过改了实现，可能引入 lint 问题）。

无法修复时记 `verification_failed`，scope 为受影响模块，不是整个需求。

**规则 3：只有必要验证全部完成才 `complete`。**

"必要验证"由 `plan.md` 的验证方案定义。人工验证项必须**经开发确认已执行且结果符合预期**，不能由 AI 单方面标记完成。

**规则 4：不能一边写"需要人工验证"一边输出"交付完成"。**

这是最常见的错误组合。两者互斥：

| 不允许的组合 | 为什么 |
| --- | --- |
| `delivery.md` 有待人工执行清单 + `stageStatus.delivery: complete` | 交付阶段不能超前于验证阶段 |
| 证据表里有"未执行"行 + 总结写"全部验证通过" | 自相矛盾，且会让开发误判可以直接上线 |
| 有 `verification_failed` 阻塞项 + `stageStatus.delivery: complete` | 必要验证未通过时交付不得完成 |

**级联规则：** `stageStatus.verification` 不是 `complete` 时，`stageStatus.delivery` 不得为 `complete`。

## 第五部分：交付清单

`delivery.md` 必须包含九项，每项都不能留空（无内容时写"无"并说明）。

| # | 项 | 要写什么 | 常见缺陷 |
| --- | --- | --- | --- |
| 1 | 完成的功能 | 按需求验收标准逐条对照：完成 / 部分完成 / 未完成，部分或未完成要写原因 | 只写"完成了 XX 功能"，无法对照验收标准 |
| 2 | 创建和修改的文件 | 准确路径 + 改动内容 + 所属项目，区分创建/修改/测试 | 只写数量不写清单 |
| 3 | 对接的接口 | 每个接口的状态：已联调 / 已按契约实现未联调 / 仍为 Mock / 未实现 | 把 Mock 写成"已对接" |
| 4 | UI 验收结果 | 逐页对照 UI 图的结果；有差异的写明差异与原因；不依赖 UI 时写"不适用" | 写"已还原"但没说在哪个尺寸下对比过 |
| 5 | 测试和构建证据 | 第三部分要求的完整证据 | 只写结论不写命令 |
| 6 | 未验证内容 | 未执行的验证项 + 原因 + 未覆盖风险 | 省略 |
| 7 | 已知风险和遗留事项 | 见第六部分 | 混为一类 |
| 8 | 对旧功能的影响 | 修改了哪些公共能力、影响哪些调用方、回归覆盖到哪些、未覆盖哪些 | 写"无影响"但改了公共文件 |
| 9 | 需要开发人工执行的操作 | 逐条可执行的操作清单 | 只写"需要人工验证" |

### 第 9 项的内容来源

需要开发人工执行的操作通常包括：

| 类型 | 例子 |
| --- | --- |
| 待人工执行的验证 | 需要账号、真机、特定环境的验证项 |
| 需要授权的操作 | 安装依赖、修改环境配置、提交、推送、建 PR、部署、发布 |
| 需要他方配合 | 后端补契约、后端修正响应、UI 补状态图、产品确认待定项 |
| 环境准备 | 配置环境变量（**值由开发填写，不写入产物文件**）、准备测试数据 |
| 联调 | Mock 切真实接口后的联调与重新验证 |

每条写清：做什么、怎么做、为什么 AI 不能做、做完后需要验证什么。

### 凭证约束

**测试账号、密码、Token、验证码、环境凭证一律不写入任何产物文件**（`delivery.md`、`context.md`、`plan.md`、`decisions.md`、`workflow-state.json` 全部适用）。

需要引用时只写"需要 X 类型的账号，由开发提供"。已经从开发那里得到的凭证也不落盘。

## 第六部分：风险评估

### 已知风险 vs 遗留事项

两者容易混，区别在于**是否存在造成问题的可能**：

| 类别 | 定义 | 特征 | 例子形态 |
| --- | --- | --- | --- |
| **已知风险** | 可能导致问题的不确定性 | 有触发条件、有后果、需要判断是否接受 | 某接口未联调，联调时字段不符会导致该功能不可用 |
| **遗留事项** | 已知的未完成或待办工作 | 无不确定性，只是还没做 | 某状态待 UI 补图后实现；某既有测试失败待团队处理 |

判断技巧：问"这件事会不会出问题？"——会，是风险；不会，只是没做完，是遗留事项。

### 风险的四要素

每条风险必须写全四项，缺任何一项开发都无法决策：

| 要素 | 要写什么 | 反例 |
| --- | --- | --- |
| 影响范围 | 具体哪个功能、哪些用户、哪些端 | "可能有影响" |
| 触发条件 | 什么情况下会出问题 | 不写触发条件，开发无法判断概率 |
| 严重度 | 高 / 中 / 低 + 判定依据 | 只写"高"不说为什么 |
| 缓解建议 | 具体可执行的措施 | "注意一下" |

**严重度判定标准：**

| 严重度 | 判定依据 |
| --- | --- |
| 高 | 涉及资金、数据写入、数据丢失、权限越界、隐私泄露；或核心流程不可用 |
| 中 | 非核心功能异常；或核心功能在特定条件下异常；或需要人工介入恢复 |
| 低 | 视觉细节、非关键提示、边缘场景体验问题 |

**风险表格形态：**

```markdown
## 已知风险

| # | 风险 | 影响范围 | 触发条件 | 严重度 | 缓解建议 |
| --- | --- | --- | --- | --- | --- |
| R1 | <接口标识> 仍为 Mock，未联调 | <具体功能> | 真实响应结构与 Mock 假设不一致时 | 高（该功能完全不可用） | 联调前先核对契约九项；切换后执行 M1、M4 |
| R2 | 修改了公共请求封装，回归只覆盖 3 个主要调用方 | 其余 <N> 个调用方 | 未覆盖的调用方使用了被改动的行为分支 | 中（部分功能异常，可回滚） | 上线前抽查其余调用方；或改为本次单独实现 |
| R3 | 未在目标机型真机验证 | 该机型用户的页面布局 | 该机型的安全区或字体渲染与开发环境不同 | 低（视觉问题，不影响功能） | 上线前用真机走一遍 M5 |

## 遗留事项

| # | 事项 | 原因 | 后续动作 | 负责方 |
| --- | --- | --- | --- | --- |
| L1 | <页面> 的失败态未实现 | 缺 UI 图（`missing_ui`，scope 为该页面） | UI 补图后实现并验证 | UI → 前端 |
| L2 | 既有测试 2 个用例失败 | 改动前即失败，非本次引入 | 由团队排期处理 | 团队 |
| L3 | 观察到 <目录> 存在未使用的旧实现 | 与本次需求无关，未删除 | 团队确认后清理 | 团队 |
```

### 风险识别的检查点

交付前逐项自查，命中即记为风险：

| # | 检查点 | 对应风险 |
| --- | --- | --- |
| 1 | 有接口未联调或仍为 Mock 吗？ | 契约不符导致功能不可用 |
| 2 | 修改了公共能力吗？回归覆盖了全部调用方吗？ | 未覆盖调用方的回归风险 |
| 3 | 有验证项未执行吗？ | 对应的未覆盖风险 |
| 4 | 有基于临时假设的实现吗？ | 假设不成立时需返工；**临时实现不得交付或部署** |
| 5 | 有 P2 问题按默认方案处理吗？ | 产品否决时按需求变更处理 |
| 6 | 需求覆盖多端但只验证了部分端吗？ | 未验证端的行为差异 |
| 7 | 涉及权限、敏感数据、写操作幂等吗？验证充分吗？ | 高严重度风险，需重点说明 |
| 8 | 有既有问题被接受了吗？ | 记录风险与接受依据 |
| 9 | 依赖某个环境配置或前置数据吗？ | 环境不一致导致的行为差异 |

## 第七部分：授权边界

### 需要单独授权的操作

以下操作**一律不自动执行**，即使开发批准了 `plan.md`（计划批准只授权修改业务代码）：

| 操作 | 为什么需要单独授权 |
| --- | --- |
| 安装依赖 | 改变依赖树与锁文件，影响全团队；涉及供应链安全 |
| 修改环境配置 | 可能影响其他环境或其他人的本地配置；可能涉及凭证 |
| 提交（commit） | 提交历史是团队共享资产；可能混入不该提交的文件 |
| 推送（push） | 影响远程分支，其他人会拉到 |
| 创建 PR / MR | 触发团队 review 流程与 CI |
| 部署 | 影响运行环境 |
| 发布 | 影响真实用户 |

### 请求授权的方式

说明三件事：要做什么、为什么必要、有什么影响与是否可回退。

```markdown
需要授权：安装依赖 <包名>@<确定的版本>

用途：<具体用途，对应 plan.md 的哪个任务>
必要性：<为什么项目现有能力无法满足>
影响：修改依赖清单与锁文件；<产物体积/构建时间等影响>
可回退：卸载并还原锁文件
包管理器：<项目实际使用的包管理器>

请确认是否执行，或由你手动安装后我继续。
```

**依赖版本要求：** 使用确定的版本，不用开放范围。包名不常见或与知名包名相似时主动提示可能的拼写混淆风险。

### 不需要单独授权的操作

| 操作 | 前提 |
| --- | --- |
| 读文件、搜代码 | 无 |
| 修改业务代码 | `approvedPlanVersion` 等于当前 `planVersion`，且在计划范围内 |
| 执行只读的验证命令（lint、类型检查、测试、构建） | 命令本身不修改源码、不安装依赖、不访问外部服务 |
| 写产物文件（五个文件） | 无 |

**注意：** 部分项目的 lint 脚本带自动修复参数，或测试脚本会写入快照文件。执行前确认命令是否会修改源码；会修改的按"修改业务代码"对待，且只在计划范围内使用。

### 不上传外部服务

不把项目源码、需求资料、UI 资料、凭证上传到任何外部服务，包括以"分析"或"格式化"为名的在线工具。

## 常见误判纠正

### 误判 1：自动验证通过就标交付完成

不对：lint、类型检查、测试、构建全绿，于是把验证和交付都标 `complete`。

正确：还有人工验证项未执行时，`stageStatus.verification` 是 `awaiting_confirmation`，`delivery.md` 列出待人工执行清单，`delivery` 不得为 `complete`。

### 误判 2：一边列待人工验证一边写"交付完成"

不对：`delivery.md` 里既有"待开发人工执行的验证"清单，又在结尾写"本次需求已交付完成"。

正确：两者互斥。有待执行项就写"待人工验证完成后方可交付"，并明确列出还差什么。

### 误判 3：项目没有测试就引入测试框架

不对：发现项目没有测试能力，装一个测试框架并写配置。

正确：引入测试框架属于新增依赖 + 扩大范围，需要单独授权。改为记录替代验证方式与未覆盖风险。

### 误判 4：顺手修复既有失败

不对：跑测试发现 2 个既有用例失败，一并修好，"反正也不难"。

正确：不擅自修复。记录可复现证据、与本次改动无关的判断、修复建议，由开发决定。修复超出批准范围且可能改变其他功能行为。

### 误判 5：既有问题被接受就写"全部通过"

不对：开发说"那 2 个失败是老问题，不用管"，于是证据里写"测试通过"。

正确：写"测试执行完成，2 个用例失败，均为既有问题（附证据），开发已接受该风险（见 `decisions.md` 记录）"。开发接受风险不改变"有失败"这个事实。

### 误判 6：猜测验证命令

不对：假设项目有某个常见脚本名，写进证据里说执行了。

正确：证据必须是**本次实际执行**的命令与结果。命令不存在或跑不起来时记"未执行"并写原因。

### 误判 7：`verification_failed` 的 scope 写整个需求

不对：一个模块的测试失败，scope 写成需求标识，导致所有工作停摆。

正确：scope 为受影响模块。其他无依赖的工作继续。

### 误判 8：把 Mock 写成已对接

不对：接口对接清单里写"全部接口已对接完成"，但其中两个仍走 Mock。

正确：逐个标状态——已联调 / 已按契约实现未联调 / 仍为 Mock / 未实现。Mock 的必须同时记为已知风险。

### 误判 9：风险只写一句话

不对：`已知风险：接口未联调可能有问题。`

正确：四要素齐全——影响范围（哪个功能）、触发条件（什么情况下出问题）、严重度（高/中/低 + 依据）、缓解建议（具体措施）。

### 误判 10：把遗留事项当风险，或反之

不对：把"某状态待 UI 补图后实现"写成风险；把"接口未联调"写成遗留事项。

正确：前者是遗留事项（确定的未完成工作，无不确定性）；后者是风险（有触发条件和后果）。

### 误判 11：自动执行提交或推送

不对：验证通过后顺手提交并推送到远程。

正确：提交、推送、建 PR、部署、发布均需单独授权。把它们写进"需要开发人工执行的操作"。

### 误判 12：把测试账号写进 delivery.md

不对：为了方便复现，把测试账号密码写进验证证据。

正确：只写"需要 X 类型账号，由开发提供"。任何产物文件都不保存凭证。

## 总结

**测试选择：**
1. 从项目脚本、CI 配置、工具配置、测试文件识别实际能力，读脚本的实际内容，不假设命令名
2. "脚本存在但跑不起来"按不具备处理并说明原因
3. 缺少能力时记录替代验证方式与具体的未覆盖风险，不引入测试框架

**覆盖范围：**
1. 十项：正常、异常、重复操作、网络、加载与空、长文本、目标屏幕、登录权限、跨端跳转、旧功能回归
2. 回归范围来自复用分析的调用方清单；改公共能力要覆盖全部调用方
3. 无法全覆盖时说明覆盖了什么、未覆盖什么、风险是什么

**证据：**
1. 五项必记：准确命令、结果、失败数量、未执行项及原因、人工验证项
2. 三种状态必须可区分：通过 / 失败 / 未执行（含原因）
3. 区分本次引入与既有问题；本次引入修复后重跑完整验证；既有问题报告不修
4. 任何未执行或失败都不得声明全部完成

**状态规则：**
1. 人工验证未执行 → `awaiting_confirmation` + 待人工执行清单
2. 本次导致失败无法修复 → `verification_failed`，scope 为受影响模块
3. 必要验证全部完成（含人工验证经开发确认）才 `complete`
4. `verification` 不是 `complete` 时 `delivery` 不得 `complete`
5. 不能一边写"需要人工验证"一边输出"交付完成"

**交付：**
1. 九项齐全，无内容写"无"并说明
2. 接口状态逐个标注，Mock 不写成已对接
3. 凭证不进任何产物文件

**风险：**
1. 已知风险有触发条件和后果；遗留事项只是未完成
2. 风险四要素：影响范围、触发条件、严重度（含依据）、缓解建议
3. 九个检查点逐项自查

**授权：**
1. 安装依赖、改环境配置、提交、推送、建 PR、部署、发布 → 一律单独授权
2. 请求授权时说明用途、必要性、影响、可回退方式
3. 计划批准只授权改业务代码，不授权以上任何一项

**判断技巧：**
- 问自己"这条结论有本次实际执行的命令和输出支撑吗？"→ 没有就是"未执行"
- 问自己"开发看完这份 `delivery.md`，知道现在能不能上线吗？"→ 不知道就说明没写清
- 问自己"这件事会不会出问题？"→ 会是风险，不会只是遗留事项
- 问自己"这个操作会影响我的工作区之外的东西吗？"→ 会就需要授权
