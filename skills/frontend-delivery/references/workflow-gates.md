# 确认与批准规则

本文定义问题分级、授权范围和确认方式。完整流程字段见 state-machine.md，产出完成条件见 testing-and-delivery.md。

## 什么时候询问

- 从用户要求、项目规范和相关代码能够确定的内容，不重复问。
- 业务规则存在多种合理解释、关键边界不明、范围扩大、公共行为变化或真实工作区冲突时，说明影响后询问。
- 已获授权在相同范围内继续有效，不能因恢复、记录迁移或流程升级要求重新授权。
- 一个实际决策允许包含互相关联的问题，一次说明完整方案；独立问题可列短清单，避免强制一问一答。
- 缺事实或资料时直接请求，不为凑选项虚构业务方案。
- 给方案时说明推荐理由、代价及是否绕过原问题。产品清单用业务语言，技术依据留在任务记录。

## 问题分级

P0：不确定性影响关键业务正确性、权限、资金、隐私或不可逆后果。
- 受影响任务及下游不得基于猜测实现；其他分析、草案和已获准的独立任务可继续。
- 由用户或有决策权限的人明确结论。开发可以是决策者，记录真实来源，不要求额外身份仪式。
- 高风险主题已有清晰规则时，核对依据和风险，不机械重新提问。

P1：影响方案、接口或验收，但可形成标注缺口的草案。
- 未解决部分不可获准实施，不阻止批准其他独立任务。
- 已有同类约定能回答的问题不再视为缺口。
- 未明确目标平台属于范围问题；只缺某平台适配细节时，限定到该平台。

P2：必要、局部、可逆的细节，有项目约定或同类实现依据。
- 可说明依据后继续，不把推断标成用户确认。
- 不包含原需求未要求的快捷键、字数统计、批量操作等新功能。
- 不因“容易修改”将业务规则降为 P2；影响法律含义或金额口径的文案也不是普通细节。
- 默认处理被否决后，按 change-control.md 判断修正或基线变化，不自动记需求变更。

## 不同流程的批准方式

小改动：
- 明确修改请求即为该范围授权，无须生成计划再批准。
- 发现关键歧义时暂停对应修改，说明升级原因。

常规需求：
- 任务、预期行为和授权范围明确即可执行。
- 真正需要选择的部分先提出可审阅方案，其他任务继续。
- 在聊天或 task.md 保留必要授权依据，不强制 JSON。

完整流程：
- 将验收项和任务划分到可独立判断的范围。
- 确认业务规则和具体任务方案，不是确认“文档已经生成”。
- 展示请求批准的任务 ID、版本、行为、影响及验证方式，列出未包含的待确认任务。
- “全部批准”只覆盖展示的可实施任务；未决 P0/P1 不因笼统批准而被默认为解决。
- “批准 T-01、T-02”只覆盖这些任务的当前版本。
- 实际批准记录和任务执行前提以 state-machine.md 为准。
- 评审或计划编写完成不赋予实现权限。只说“计划没问题”且原终点为 planning_only 时，不自行开始编码。

## 授权延续与撤回

“按这个方案开始实现”可同时表达方案批准和终点升级，不要求重复确认。
已授权范围内且不改变约定的实现细节调整可继续，扩大范围或改变行为、契约、关键方案、依赖责任、风险及验收标准时再核对受影响批准。完整流程的任务版本边界见 state-machine.md；其他流程沿用当前授权记录。批准延续不代表旧验证证据仍有效。
用户缩小范围或撤回授权后不再执行该范围；已完成代码和记录不自动删除或回滚。
项目禁止测试、安装或 Git 写操作时，普通计划批准不能覆盖禁令。明确单项授权仅适用于实际授权的动作。
