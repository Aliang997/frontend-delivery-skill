## 第一部分：UI 依赖判定

阶段二第一件事是判断本次需求是否依赖 UI。判定结果决定后续走向，不能跳过。

### 判定表

| 需求类型 | 是否依赖 UI | 理由 |
| --- | --- | --- |
| 页面新增 | 依赖 | 布局、层级、间距、状态展示都无从推断 |
| 页面改版 | 依赖 | 需要对比新旧稿确定改动边界 |
| 视觉还原 | 依赖 | 还原本身就是以 UI 为准 |
| 布局调整 | 依赖 | 调整后的目标布局必须有依据 |
| 样式优化 | 依赖 | 颜色、字号、圆角、阴影需要确定值 |
| 组件新增 | 依赖 | 组件的视觉与交互状态需要设计定义 |
| 接口调整 | 不依赖 | 只改数据来源与结构，界面不变 |
| 埋点 | 不依赖 | 只加上报调用，无视觉变化 |
| 纯逻辑修改 | 不依赖 | 计算、校验、状态流转不改界面 |
| 不涉及视觉的 Bug 修复 | 不依赖 | 修的是行为，不是外观 |
| 配置修改 | 不依赖 | 环境、常量、构建配置无界面 |

### 混合需求的处理

一个需求同时包含依赖 UI 和不依赖 UI 的部分时，**按任务逐个判定，不按需求整体判定**。

例：需求包含"新增筛选面板"（依赖 UI）和"修正金额计算逻辑"（不依赖 UI）。缺 UI 时只阻塞筛选面板相关任务，金额计算任务照常执行。

判定粒度就是 `plan.md`"技术任务及依赖"里的任务粒度。这样 `missing_ui` 的 scope 才能落到具体任务上。

### 判定为不依赖时

把 `plan.md` 的"UI与资源映射"章节标为"不适用"，并写一句理由：

```markdown
## UI与资源映射

不适用。本次需求为接口字段调整与埋点补充，不涉及界面变化。
```

不要留空，也不要删掉章节。标注"不适用"是一个明确结论，留空是信息缺失，两者不同。

### 判定为依赖但缺 UI 时

**记范围级 `missing_ui` 阻塞项**，scope 为具体页面或任务，不是整个需求：

```json
{
  "code": "missing_ui",
  "scope": "<项目名>/<页面或任务标识>",
  "createdAt": "<带时区的 ISO 8601 时间>",
  "details": "页面新增任务缺少设计稿，无法确定布局与状态展示"
}
```

**只停该范围及其下游依赖，其他任务继续。** 判断下游的依据是 `plan.md`"技术任务及依赖"里的依赖链：依赖被阻塞任务的任务一并暂停，不依赖的任务保持 `active`。

只有全部剩余任务都无法推进时，全局 `status` 才为 `blocked`。

**同时在 `context.md` 列出所需的 UI 资料清单**，让开发或 UI 知道要补什么：

```markdown
### 缺少的 UI 资料

| # | 需要的内容 | 类型 | 用于 | 阻塞任务 |
| --- | --- | --- | --- | --- |
| UI-01 | 目标页面主视图 | 页面图 | 布局、间距、字号、层级 | T2 |
| UI-02 | 列表加载中的展示 | 状态图 | 骨架屏还是转圈的判断 | T2 |
| UI-03 | 列表无数据的展示 | 状态图 | 插图、文案、是否有操作按钮 | T2 |
| UI-04 | 请求失败的展示 | 状态图 | 提示位置、是否有重试入口 | T2 |
| UI-05 | 表单项校验失败的展示 | 交互图 | 提示位置与触发时机 | T3 |
```

清单要具体到"哪个页面的哪个状态"，"请提供 UI 图"这种笼统说法无法执行。

### 不得为缺失的关键 UI 状态自行创造设计

这是硬约束。自行创造的设计会被当成已确认结论进入实现，返工成本比等 UI 高。

| 缺失内容 | 可以做 | 不可以做 |
| --- | --- | --- |
| 加载态 | 记为缺失项，说明需要"骨架屏 / 转圈 / 顶部进度条"中的哪一种 | 自己挑一种画出来并实现 |
| 空数据态 | 记为缺失项，列出需要确定的元素（插图、文案、操作按钮） | 自己编文案和插图 |
| 失败态 | 记为缺失项，说明需要确定提示形式与重试入口 | 自己设计一套错误页 |
| 主视图布局 | 记为缺失项，阻塞该页面任务 | 参考同类页面"推测"一版布局 |

**"关键"的界定：** 影响用户能否完成主流程、影响信息层级、影响可点击区域的，都是关键。

**可以按项目既有约定处理的（不算创造设计）：** 项目里已有统一的加载组件、空状态组件、错误提示组件，且本页面属于同类场景时，可以沿用并在 `plan.md` 明确写出"沿用项目既有 X 组件，待 UI 确认"。这是复用既有决策，不是创造新设计。区别在于——沿用有依据且可指出来源，创造没有。

## 第二部分：本地 UI 与切图分析

首版只读取开发提供的本地目录（`uiDir` 与 `assetsDir`）。使用当前环境的图片检查能力读取图片；不具备图片检查能力时，说明受影响范围并请开发提供文字说明或手动补充信息。

### 要提取的信息

**UI 图层面：**

| 提取项 | 用途 | 记录位置 |
| --- | --- | --- |
| 图片名称 | 建立图与页面/状态的对应关系 | `plan.md` UI与资源映射 |
| 图片尺寸 | 判断设计基准宽度、是否为多倍图、目标端 | `plan.md` UI与资源映射 |
| 更新时间 | 同一页面存在多版时判断哪版最新 | `plan.md` UI与资源映射 |
| 对应页面或状态 | 映射关系是后续所有 UI 工作的基础 | `plan.md` UI与资源映射 |

**视觉规格层面：**

| 提取项 | 需要确定到什么程度 |
| --- | --- |
| 页面布局 | 区块划分、层级关系、对齐方式、内容顺序 |
| 颜色 | 主色、辅色、文字色、背景色、边框色、状态色。优先对应项目已有的设计变量 |
| 字体 | 字号、字重、行高、字体族。优先对应项目已有的排版变量 |
| 间距 | 区块间距、元素间距、内边距。识别是否符合项目的间距梯度 |
| 圆角 | 各类元素的圆角值，是否统一 |
| 阴影 | 卡片、弹层、悬浮按钮的阴影层级 |

**行为与适配层面：**

| 提取项 | 要回答的问题 |
| --- | --- |
| 响应式 | 有几个断点？各断点下布局如何变化？是否有仅某端显示的元素？ |
| 安全区 | 顶部状态栏、底部手势区是否需要留白？沉浸式还是普通模式？ |
| 滚动 | 哪个区域滚动？是否有嵌套滚动？是否有下拉刷新或上拉加载？ |
| 吸顶吸底 | 哪些元素吸顶或吸底？吸附的触发位置在哪？ |
| 键盘行为 | 键盘弹起时布局如何变化？输入框是否被遮挡？是否需要自动滚动？ |

**未展示状态层面：** 逐页检查加载、空数据、失败、无权限、部分数据缺失这几种状态是否有对应图。缺失的按"缺少的 UI 资料"清单记录。

### 如何把 UI 图映射到页面与状态

用两类线索交叉判断，不要只依赖一类。

**命名线索：**

| 命名特征 | 通常含义 | 注意 |
| --- | --- | --- |
| 序号前缀（01、02） | 流程顺序或页面顺序 | 序号不一定等于实现顺序 |
| 页面名词（列表、详情、编辑） | 页面类型 | 中英文混用时两种都要搜 |
| 状态后缀（空、加载、失败、异常、默认） | 页面状态图 | "默认"可能指正常态，也可能指未选中态，需结合内容确认 |
| 端标识（H5、PC、小程序、移动） | 目标运行端 | 与项目实际运行端对不上时要询问 |
| 版本标识（v2、新、修改后、终） | 版本 | 多个"终版"时以更新时间为准，并询问开发确认 |

**内容线索：**

1. 图中的页面标题、导航文字，与需求文档中的页面名对应。
2. 图中的列表项数量：0 项通常是空态，1-3 项通常是正常态示意，很多项可能是滚动或分页示意。
3. 图中是否有骨架块、转圈、灰色占位 → 加载态。
4. 图中是否有插图 + 单行文案 + 可能的按钮 → 空态或失败态；区分依据是文案语义。
5. 图中是否有红色文字、警示图标 → 校验失败或错误态。
6. 图中被高亮或框选的区域 → 本次改动重点（改版需求常见）。

**映射结论的写法：** 在 `plan.md` 里建立一张表，每张图一行，映射不确定的显式标出。

```markdown
## UI与资源映射

### 页面图映射

| UI 图 | 尺寸 | 更新时间 | 对应页面 | 对应状态 | 置信度 |
| --- | --- | --- | --- | --- | --- |
| <图片文件名> | <宽x高> | <日期> | <页面名> | 正常 | 确定 |
| <图片文件名> | <宽x高> | <日期> | <页面名> | 空数据 | 确定 |
| <图片文件名> | <宽x高> | <日期> | <页面名> | 未确定（疑似加载态） | 待确认 |
```

置信度为"待确认"的映射不能直接进入实现，要写入 `context.md` 开放问题询问。

### 切图分析

**要提取的信息：** 文件名、格式、尺寸（含倍图标识）、可能用途、建议存放位置。

**用途推断线索：**

| 线索 | 推断用途 |
| --- | --- |
| 尺寸小且为正方形，成组出现 | 图标集 |
| 文件名含状态词（选中/未选中、开/关、亮/暗），成对出现 | 状态切换图标 |
| 尺寸大且宽高比接近页面 | 背景图或插画 |
| 尺寸中等、带透明区域、单独出现 | 空态或结果页插图 |
| 同名多倍图（同名 + 倍数后缀） | 同一资源的多分辨率版本 |
| 矢量格式 | 图标，通常可直接内联或作为字体图标使用 |
| 文件名与页面名相同 | 该页面专属资源 |

**存放位置建议：** 按项目现有约定给出建议路径，不自创目录结构。先搜项目里现有的图片资源放在哪、按什么规则分目录（按业务分 / 按类型分 / 集中放），然后沿用。

```markdown
### 切图映射

| 切图 | 格式 | 尺寸 | 推断用途 | 建议存放位置 | 用于页面 |
| --- | --- | --- | --- | --- | --- |
| <文件名> | <格式> | <宽x高> | 空态插图 | <按项目现有约定的路径> | <页面名> |
```

推断用途不确定时标"待确认"，不要硬填一个用途。

### UI 图与切图的缺失、重复、冲突

| 问题类型 | 如何识别 | 处理 |
| --- | --- | --- |
| 缺失 | UI 图里出现的图标或插图，切图目录里找不到对应资源 | 列入缺失清单，问是否需要 UI 补切图，或确认可用项目现有资源代替 |
| 重复 | 同一资源多个文件名或多个版本，内容看起来相同 | 列出全部候选，问用哪个；不自行选择 |
| 冲突 | 同一页面多张图布局不一致；切图尺寸与 UI 图中的显示尺寸差异明显；UI 图与需求文档描述矛盾 | 记为待确认，**不自行取舍**。UI 与需求矛盾时属于必须暂停的情形 |
| 多余 | 切图目录里有本次需求用不到的资源 | 记录但不引入项目。多余资源不要"顺手"加进仓库 |

### UI 资料存在但信息不足

有 UI 图不等于信息充分。下面这些情况即使有图也要记缺失项并询问：

| 情况 | 缺什么 | 询问对象 |
| --- | --- | --- |
| 只有一张主视图，无状态图 | 加载、空、失败态 | UI 或产品 |
| 图是静态截图，无交互说明 | 点击后的跳转与反馈、动画时长 | UI 或产品 |
| 只有一个端的图，需求覆盖多端 | 其他端的适配方案 | UI |
| 图上文字被截断或用占位符 | 真实文案与超长文案的处理 | 产品 |
| 长列表只画了 3 项 | 分页方式、加载更多的形态 | 产品 |
| 图中数据明显是假数据，字段与接口对不上 | 字段与展示的对应关系 | 产品或后端 |
| 缺少设计基准宽度信息 | 适配换算基准 | UI |

**记录方式：** 与"缺少的 UI 资料"清单同一张表，区分"完全没有"和"有但不足"，因为后者往往一句说明就能解决，优先级排前面。

## 第三部分：生成技术计划

### plan.md 章节顺序

必须按此顺序，每个章节都存在（不适用时标"不适用"并写理由）：

```markdown
## 目标与非目标

## UI与资源映射

## 需要创建的文件

## 需要修改的文件

## 数据流和页面状态

## API对接清单

## 技术任务及依赖

## 验证方案

## 不允许修改的范围
```

各章节要点：

| 章节 | 要写什么 | 常见缺陷 |
| --- | --- | --- |
| 目标与非目标 | 本次做什么、明确不做什么。非目标来自 `context.md` 的"需求明确不做" | 只写目标不写非目标，导致范围蔓延 |
| UI与资源映射 | 第二部分产出的映射表；不依赖 UI 时标"不适用" | 留空 |
| 需要创建的文件 | 准确路径 + 一句用途 | 用目录代替文件、路径含通配符 |
| 需要修改的文件 | 准确路径 + 改什么 + 改动量 | 只写路径不写改什么，无法评估风险 |
| 数据流和页面状态 | 数据从哪来、经过什么、存在哪；每个页面有哪些状态及切换条件 | 只画数据流不列状态，或反之 |
| API对接清单 | 每个接口的用途、所属项目、契约来源、是否已确认 | 编造未确认的契约细节 |
| 技术任务及依赖 | 任务清单 + 依赖顺序。多项目时标注归属 | 没有依赖关系，导致阻塞时无法判断下游 |
| 验证方案 | 见"验证方案的 6 项要求" | 只写命令不写通过标准 |
| 不允许修改的范围 | 明确不能碰的文件或目录及原因 | 遗漏开发未提交修改涉及的文件 |

### 文件清单要求

| 要求 | 说明 | 正确示例形态 | 错误示例形态 |
| --- | --- | --- | --- |
| 准确路径 | 从项目根开始的完整相对路径，含文件扩展名 | `src/<目录>/<文件名>.<扩展名>` | `src/pages/` 或 `新建页面文件` |
| 区分类型 | 创建 / 修改 / 测试文件分开列 | 三个独立子清单或明确标记 | 混在一个列表里 |
| 标注项目 | 多项目时每个文件前标项目名 | `[<项目名>] <路径>` | 只写路径，无法判断属于哪个项目 |
| 说明用途 | 创建文件写用途，修改文件写改什么 | `<路径>：新增 N 条路由配置` | `<路径>：修改` |
| 扩展名符合项目 | 从项目现有同类文件确定扩展名与命名风格 | 与项目现有文件一致 | 按自己习惯写扩展名 |

**测试文件单独列：** 测试文件放在"需要创建的文件"里但明确标记为测试，或单独设子清单。命名与位置要遵循项目现有测试文件的约定（先搜项目里现有测试放在哪、怎么命名）。

**归属规则（多项目）：** 文件属于"包含它且路径层级最深"的项目根目录，不按 `projectPaths` 的声明顺序。

### 接口处理的四条边界

这是阶段二最容易出错的地方，四条边界必须同时遵守。

| # | 边界 | 说明 |
| --- | --- | --- |
| 1 | **可以**识别需要哪些业务接口 | 从需求和 UI 推断出需要"获取列表""提交表单""上传文件"这类业务能力，写进 API 对接清单 |
| 2 | **可以**列出待后端确认的问题 | 分页参数形式、错误码含义、字段可空性、排序规则、鉴权方式，都可以列成问题清单 |
| 3 | **不得**编造 URL、方法、字段或错误码 | 没有后端确认的契约就是没有。写下一个"看起来合理"的路径或字段名，后面所有代码都建立在虚构之上 |
| 4 | 契约缺失时记 `missing_api_contract` | scope 为**对应接口任务**，只阻塞该任务，其余任务继续 |

**API 对接清单的正确写法（契约未确认时）：**

```markdown
## API对接清单

| # | 业务用途 | 所属项目 | 契约来源 | 状态 | 阻塞任务 |
| --- | --- | --- | --- | --- | --- |
| API-01 | 获取目标列表数据 | <项目名> | 接口文档已提供 | 已确认 | - |
| API-02 | 提交表单数据 | <项目名> | 无 | **契约缺失** | T4 |

### 待后端确认的问题

| # | 关联接口 | 问题 | 影响 |
| --- | --- | --- | --- |
| API-Q1 | API-02 | 请求方法、路径与参数结构 | 无法编写请求代码 |
| API-Q2 | API-02 | 业务错误码清单及各码的用户提示 | 无法实现失败分支 |
| API-Q3 | API-02 | 重复提交由哪一端保证幂等 | 决定前端是否需要请求锁 |
```

注意 API-02 行没有填任何路径和字段——这是正确的。**留空比填一个猜测值安全。**

**契约已确认时**才写具体的方法、路径、参数、响应结构，并注明来源（接口文档的哪一节 / 后端在什么时间确认的）。

**接口文档存在但与 UI 或需求矛盾时**，不属于"契约缺失"，属于必须暂停的情形（见下文）。

### 数据流和页面状态

**数据流要回答：** 数据从哪个接口或本地来源获取 → 在哪一层处理转换 → 存在组件内还是全局 → 谁消费 → 何时失效或刷新。

**页面状态要回答：** 每个页面/弹窗有哪些状态、各状态的进入条件、状态之间能否直接切换。

用文字或简单箭头表述，不要写框架代码：

```markdown
### 数据流

<列表数据>：接口 API-01 → 统一请求层 → 页面局部状态 → 列表组件
  刷新时机：页面进入、筛选条件变化、提交成功后

<用户身份信息>：项目现有登录态（复用，不新增存储）→ 页面读取用于权限判断

### 页面状态

<页面名>：
- 加载中：进入页面且首次请求未返回
- 正常：请求成功且数据非空
- 空数据：请求成功且数据为空
- 失败：请求失败（含超时）
- 无权限：身份校验不通过（进入页面前判断，不发起数据请求）

状态切换：加载中 → 正常/空数据/失败；失败 → 加载中（点击重试）
```

### 技术任务及依赖

任务是阻塞与失效的最小单位，粒度直接影响范围级阻塞是否好用。

| 要求 | 说明 |
| --- | --- |
| 任务有 ID | `T1`、`T2` 便于在阻塞项、失效项、验证方案里引用 |
| 依赖关系明确 | 用箭头或前置任务字段表示。没有依赖的任务显式标"无" |
| 粒度适中 | 一个任务对应一个可独立验证的产出。太粗则阻塞范围过大，太细则依赖图难维护 |
| 标注项目 | 多项目时标明任务在哪个项目执行 |
| 跨项目依赖单独写 | 跨项目的跳转参数、接口契约、发布顺序、联调依赖都写在本章节 |

```markdown
## 技术任务及依赖

| 任务 | 项目 | 内容 | 前置 | 关联接口 | 关联 UI |
| --- | --- | --- | --- | --- | --- |
| T1 | <项目名> | 新增接口请求方法 | 无 | API-01 | - |
| T2 | <项目名> | 新增页面骨架与布局 | 无 | - | UI-01 |
| T3 | <项目名> | 列表数据渲染与状态处理 | T1, T2 | API-01 | UI-01~UI-04 |
| T4 | <项目名> | 表单提交 | T2 | API-02（契约缺失） | UI-05 |
| T5 | <项目名> | 补充测试 | T3, T4 | - | - |

### 跨项目依赖

- <项目A> 的跳转参数格式需与 <项目B> 的接收逻辑一致，联调前双方确认参数名与编码方式
- 两个项目共用 API-01，契约变化时同步更新两侧
```

### 验证方案的 6 项要求

验证方案是阶段四的执行依据，6 项缺一不可。

| # | 要求 | 具体写什么 | 常见缺陷 |
| --- | --- | --- | --- |
| 1 | 需要运行的准确命令 | 从项目脚本字段确认的实际命令，含参数与工作目录。多项目时每条命令标注在哪个项目执行 | 写通用命令名而不核对项目脚本，导致命令根本不存在 |
| 2 | 每项命令的通过标准 | 退出码、允许的失败数量、覆盖率门槛、构建产物是否生成 | 只写"通过即可"，无法判定 |
| 3 | 手动验证项 | 登录、权限、真机、视觉对比、跨端跳转等无法自动化的项，逐条写清操作步骤与预期结果 | 只写"手动验证一下"，交付时无法核对 |
| 4 | 需要的测试账号、权限、环境和测试数据 | 需要几种角色的账号、需要什么环境、需要什么前置数据。**账号密码与 Token 由开发提供，不得写入任何产物文件** | 把凭证写进 `plan.md` |
| 5 | 验证顺序、前置条件与跨项目依赖 | 先跑什么后跑什么、每项的前置条件、跨项目验证的先后关系 | 不写顺序，导致构建前没跑类型检查、白跑一轮 |
| 6 | 项目缺少某类测试能力时的替代验证方式与未覆盖风险 | 明确写"项目无 X 能力，改用 Y 验证，未覆盖 Z 风险" | 假装项目有该能力，或直接省略该类验证 |

**判断项目具备哪些能力：** 从项目脚本字段与测试配置识别，不假设命令名，不假设某个测试框架一定存在。识别方法见 `testing-and-delivery.md`。

**验证方案示例结构：**

```markdown
## 验证方案

### 自动验证

| # | 项目 | 命令 | 通过标准 | 前置条件 |
| --- | --- | --- | --- | --- |
| V1 | <项目名> | <项目脚本中的 lint 命令> | 退出码 0，本次改动文件 0 error 0 warning | 无 |
| V2 | <项目名> | <项目脚本中的类型检查命令> | 退出码 0，0 个类型错误 | 无 |
| V3 | <项目名> | <项目脚本中的测试命令> | 退出码 0，0 个失败用例 | V2 通过 |
| V4 | <项目名> | <项目脚本中的构建命令> | 退出码 0，产物目录生成预期文件 | V1、V2 通过 |

执行顺序：V1 → V2 → V3 → V4

### 手动验证

| # | 验证项 | 操作步骤 | 预期结果 | 需要的条件 |
| --- | --- | --- | --- | --- |
| M1 | 正常流程 | 登录后进入目标页 → 完成主操作 | 操作成功，列表更新 | 普通用户账号（由开发提供） |
| M2 | 无权限 | 用无权限角色进入目标页 | 展示无权限提示，不发起数据请求 | 受限角色账号（由开发提供） |
| M3 | 弱网加载 | 限速后进入页面 | 展示加载态，不出现空白 | 浏览器限速能力 |
| M4 | 重复提交 | 连续快速点击提交 | 只产生一次提交 | 测试环境 |
| M5 | 视觉对比 | 目标屏幕下对比 UI 图 | 布局、间距、字号一致 | UI 图 |
| M6 | 旧功能回归 | 走一遍受影响的既有流程 | 行为与改动前一致 | 依据复用分析的调用方清单 |

### 缺少的测试能力与替代方案

| 缺少的能力 | 替代验证方式 | 未覆盖风险 |
| --- | --- | --- |
| 端到端自动化测试 | 手动执行 M1~M4 | 无法在每次改动后自动回归，依赖人工执行 |
| 视觉回归对比 | 手动执行 M5 | 细微像素差异可能遗漏 |

### 需要的账号与环境

- 需要普通用户与受限角色两种账号：由开发提供，不写入本文件
- 需要测试环境访问权限：由开发提供
- 需要前置数据：至少 1 条已有记录与 1 个空数据场景
```

### 不允许修改的范围

明确列出不能碰的文件或目录及原因。来源有三类：

1. 开发未提交修改涉及的文件（避免覆盖开发的工作）。
2. 开发明确说过不要改的部分。
3. 与本次需求无关但容易被顺手改动的公共文件。

```markdown
## 不允许修改的范围

| 范围 | 原因 |
| --- | --- |
| <文件路径> | 开发有未提交修改，本次不触碰 |
| <目录路径> | 与本次需求无关的其他业务模块 |
| <公共配置文件> | 修改会影响全项目，需单独授权 |
```

### 计划阶段必须暂停的情形

| # | 情形 | 为什么必须暂停 | 暂停时提供什么 |
| --- | --- | --- | --- |
| 1 | 需要新增依赖 | 引入依赖影响构建体积、安全审计、团队技术选型，超出单个需求的决策范围 | 依赖用途、可否用项目现有能力实现、不引入的代价 |
| 2 | 需要扩大修改范围 | 范围是门禁二批准的核心内容，扩大等于批准失效 | 原范围、需要扩大到哪、为什么必须扩大 |
| 3 | 需要改变公共请求、登录、权限或组件行为 | 影响面超出本次需求，回归成本由开发承担 | 调用方清单、改动内容、是否向后兼容、单独实现的备选方案 |
| 4 | 现有实现与确认的需求冲突 | 冲突意味着"需求错了"或"现有实现错了"，两种结论的处理方式完全不同 | 现有实现的行为、需求要求的行为、差异点、可能的原因 |
| 5 | 有更简单的实现，但会改变已确认方案 | 已确认方案可能有你不知道的约束（其他团队依赖、历史决策） | 已确认方案、更简单方案、两者差异与取舍 |
| 6 | API 文档与 UI 或需求相互矛盾 | 三份资料互相矛盾时，任何一个选择都可能错 | 三方各自的说法、矛盾点、影响的功能 |

暂停时的动作：把未确认事实、影响和建议选项写入 `context.md` 开放问题 → 新增对应范围的阻塞项（如适用）→ 向开发提问（一次一个关键问题）→ 确认后追加 `decisions.md` 并更新 `plan.md`。

### "需要新增依赖"的粒度

不是所有依赖变化都要暂停。判断标准是**"这是否引入了项目当前不具备的新能力"**。

| 情形 | 是否暂停 | 理由 |
| --- | --- | --- |
| 升级项目已有依赖的补丁或次版本 | 不暂停 | 同类能力，无新增技术面 |
| 安装项目已有依赖的官方配套包（同一生态、同一维护方、为使用已有依赖的既有功能所必需） | 不暂停 | 属于已选技术栈的组成部分 |
| 补装项目已声明但本地缺失的依赖 | 不暂停 | 恢复既有状态，不是新增 |
| 引入项目当前没有的能力（新的状态管理、新的 UI 库、新的图表库、新的日期库、新的请求库） | **暂停** | 属于技术选型决策 |
| 引入与项目现有依赖功能重叠的包 | **暂停** | 造成两套并存，长期维护成本高 |
| 升级依赖的主版本 | **暂停** | 主版本通常含破坏性变更，影响面不可控 |
| 引入仅用于本次需求的一次性工具包 | **暂停** | 收益局限，成本长期 |

**注意：** "不暂停"只表示计划里可以写这一步，**不表示可以自动执行安装**。安装依赖始终需要单独授权（见 `testing-and-delivery.md` 的授权边界）。

**判断技巧：** 问自己"这个包提供的能力，项目里已经有别的包在做同样的事吗？"——有就暂停（重叠）；没有就是新能力，也要暂停。只有"同一生态内的配套与版本维护"才不暂停。

### 估时不属于 plan.md

这一条容易混淆，明确记住：

| 项目 | 归属 | 是否影响 planVersion |
| --- | --- | --- |
| 技术任务及依赖 | `plan.md` | 影响 |
| 文件清单 | `plan.md` | 影响 |
| 验证方案 | `plan.md` | 影响 |
| **任务拆分与小时估算** | **`context.md` 的按需附录** | **不影响** |

规则：

1. **估时不是默认交付内容。** 只有开发明确提出"拆任务""估小时""排期"时才产出。
2. **估时写在 `context.md` 的"可选：任务拆分与估时"章节**，不写进 `plan.md`。
3. **估时变化不更新 `planVersion`，不需要重新批准，不阻塞实现。**
4. **例外：** 如果估时过程暴露了新的范围或依赖（发现漏了一个任务、发现一个跨项目依赖），必须先更新 `plan.md`，此时更新 `planVersion` 并重新请求批准。触发重批的是范围变化，不是估时本身。

## 常见误判纠正

### 误判 1：因为缺 UI 就把整个需求标为阻塞

不对：一个任务缺 UI，把 `status` 直接设为 `blocked`，所有工作停摆。

正确：`missing_ui` 的 scope 是具体页面或任务。只停该范围及依赖它的下游任务，其他任务继续。只有全部剩余任务都无法推进时全局才 `blocked`。

### 误判 2：为缺失的状态"合理推测"一版设计

不对：UI 没给空态，参考同类 App 画一个插图加文案。

正确：记为缺失项并询问。可以做的是"沿用项目已有的空状态组件"并标注待 UI 确认——因为这有依据且可追溯；凭想象设计没有依据。

### 误判 3：在 API 清单里填猜测的路径和字段

不对：后端没给契约，先按 RESTful 惯例写一个路径和一组字段名，"等确认了再改"。

正确：留空，记 `missing_api_contract`，把要问的写进"待后端确认的问题"。猜测值一旦写进文档就会被当成结论，后面的代码、Mock、测试全部建立在虚构之上，返工范围远大于等待成本。

### 误判 4：验证方案只写命令不写通过标准

不对：`验证方案：运行 lint、测试、构建`。

正确：每条命令都要有可判定的通过标准（退出码、失败数量、覆盖率门槛、产物是否生成）。没有标准的验证在阶段四无法判定结果，最后只能写一句含糊的"验证通过"。

### 误判 5：猜测项目的验证命令名

不对：假设项目一定有某个常见的脚本名，直接写进验证方案。

正确：读项目脚本字段确认实际存在的命令和它们的实际内容。脚本名相同但内容不同的情况很常见（同一个名字可能只跑了部分检查）。

### 误判 6：把估时写进 plan.md 并触发重新批准

不对：开发要估时，于是在 `plan.md` 加一章工时表，更新 `planVersion`，请开发重新批准。

正确：估时写在 `context.md` 附录，不改 `planVersion`，不重批。只有估时暴露了新范围或依赖时才更新 `plan.md` 并重批。

### 误判 7：为了"更好的实现"擅自扩大范围

不对：分析时发现现有代码可以顺手优化，把它写进计划一起做。

正确：属于"需要扩大修改范围"，必须暂停询问。可以在 `context.md` 记录这个观察作为遗留建议，但不自行纳入本次范围。

### 误判 8：多项目时文件清单不标项目

不对：列一堆路径，但不说明各属于哪个项目（多项目下相同的相对路径可能在两个项目里都存在）。

正确：每个文件、任务、接口、验证命令都标注项目。归属按"包含该文件且路径层级最深的项目根目录"判断。

### 误判 9：把"不适用"和"留空"混同

不对：不依赖 UI 时直接删掉 UI 章节，或留一个空标题。

正确：保留章节，写"不适用"加一句理由。这样恢复会话或开发审阅时能确认这是判断结果，不是遗漏。

---

## 总结

**UI 依赖判定：**
1. 页面/视觉/布局/样式/组件类 → 依赖；接口/埋点/逻辑/配置/非视觉 Bug → 不依赖
2. 混合需求按任务逐个判定，不按需求整体判定
3. 不依赖时 UI 章节标"不适用"加理由，不留空
4. 依赖但缺 UI 时记范围级 `missing_ui`，只停该范围及下游
5. 绝不为缺失的关键状态创造设计；沿用项目既有组件要标注待确认

**UI 与切图分析：**
1. 三层提取：图元信息、视觉规格、行为与适配
2. 命名线索 + 内容线索交叉判断映射，不确定的标"待确认"
3. 切图存放位置沿用项目现有约定，不自创目录
4. 缺失/重复/冲突都记录询问，不自行取舍
5. "有图但信息不足"要单独记，它通常一句说明就能解决

**技术计划：**
1. 九个章节按序齐全，不适用的标注理由
2. 文件清单用准确路径，区分创建/修改/测试，多项目标注归属
3. 接口四条边界：可识别、可提问、不编造、缺失记范围级阻塞
4. 验证方案六项齐全，命令来自项目实际脚本，每项有通过标准
5. 六种情形必须暂停；新增依赖看"是否引入新能力"
6. 估时属于 `context.md` 附录，不改 `planVersion`

**判断技巧：**
- 问自己"这个视觉/交互结论有出处吗？"→ 没有就是自行创造，必须问
- 问自己"这个接口字段是谁确认的？"→ 说不出来就不能写
- 问自己"阶段四能凭这条验证项判定通过或失败吗？"→ 不能就重写
- 问自己"这个包提供的能力项目里有吗？"→ 无论有没有，涉及新增就暂停
