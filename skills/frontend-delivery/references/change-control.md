# 需求变更控制

本文档定义变更的分类标准、影响分析方法、不同时间点的处理方式、状态与门禁规则、记录格式和编号规则。

收到新信息后**先分类，再处理**。不能把所有变化都当成需求变更——过度升级会造成无意义的重批和返工；过度降级会让实现偏离已确认基线而无人察觉。

状态字段语义见 `state-machine.md`；恢复流程见 `recovery-scenarios.md` 场景九。

## 五种变化类型

| 类型 | 判断标准 | 处理方式 | 编号前缀 |
| --- | --- | --- | --- |
| 需求澄清 | 只补充原意，不改变功能、范围和验收标准 | 更新 `context.md` 并追加决策；计划未受影响时无需重批 | `DEC-*` |
| 需求变更 | 改变功能、业务规则、接口、范围或验收标准 | 创建变更记录，执行影响分析，更新需求基线和计划 | `CR-*` |
| UI 变更 | 改变布局、交互、切图、页面状态或适配要求 | 重新分析受影响 UI、资源、代码和视觉验证 | `UCR-*` |
| 技术调整 | 需求不变，只改变实现方案 | 更新 `plan.md`；影响已批准计划时重新批准 | `TECH-*` |
| 缺陷修复 | 当前实现不符合已确认需求 | 作为缺陷处理，不抬高为需求变更；补测试并验证 | `DEV-*` 或不单独编号 |

### 需求澄清 vs 需求变更（关键边界）

这是最容易判错的一对。判断标准只有一句：

> **原需求的文字是否已经隐含了这个结论？**
>
> - 隐含了，只是没写清 → **需求澄清**
> - 没隐含，或与原文字矛盾 → **需求变更**

三个辅助检验，任一命中即为需求变更：

1. **验收标准要改吗？** 要改 → 需求变更
2. **已写的代码要动吗？** 要动 → 需求变更
3. **测试用例要增删或改断言吗？** 要 → 需求变更

三项全否，才是澄清。

**对照示例：**

| 原需求 | 新信息 | 分类 | 理由 |
| --- | --- | --- | --- |
| "昵称支持中英文" | "中文按 1 个字符计，不按 2 个字节" | 需求澄清 | 原文已含"支持中英文"，只是补充计数口径；如果代码本来就按字符计，无需改动 |
| "昵称支持中英文" | "昵称最长从 20 改为 40" | 需求变更 | 改变了业务规则，校验逻辑、接口约束、测试断言都要动 |
| "列表支持分页" | "每页默认 20 条" | 需求澄清 | 分页必然有页大小，补充默认值不改变功能 |
| "列表支持分页" | "列表改为滚动加载，不要分页器" | 需求变更 | 改变交互模式和实现方案，验收标准要改 |
| "保存失败要提示用户" | "提示用 Toast，停留 3 秒" | 需求澄清（或 UI 变更） | 原文已要求提示，补充呈现方式；如果 UI 图已定义提示样式且此处与之冲突，按 UI 变更处理 |
| "保存失败要提示用户" | "保存失败要自动重试 3 次后再提示" | 需求变更 | 新增了重试行为，是新功能点 |
| "未登录跳转登录页" | "登录成功后回到原页面" | 需求变更 | 新增回跳能力，路由和状态保存都要改 |
| "支持导出数据" | "导出的是当前筛选结果，不是全量" | 需求变更 | 改变了数据边界，接口参数和验收标准都变 |
| "资料页展示头像和昵称" | "头像不存在时展示默认头像" | 需求澄清 | 边界情况的合理补充，原意未变；若原本没有默认头像资源则需 UI 补图 |

**灰区处理：** 判不准时**按需求变更处理**。代价不对称——把变更误判为澄清会导致实现偏离基线且无记录；把澄清误判为变更只是多走一次重批。

### 需求变更 vs 缺陷修复

| 事实 | 分类 |
| --- | --- |
| 已确认需求要求"未登录跳登录页"，实现里没跳 | 缺陷修复 |
| 已确认需求要求"昵称最长 20"，实现里写了 50 | 缺陷修复 |
| 已确认需求要求"昵称最长 20"，产品现在要 40 | 需求变更 |
| UI 图上按钮在右下角，实现放在了右上角 | 缺陷修复 |
| UI 图改版，按钮从右下角移到底部通栏 | UI 变更 |

判断标准：**拿已确认基线（`context.md` 的已确认需求 + `decisions.md` + UI 图）对照实现。** 实现不符合基线 → 缺陷。基线本身要改 → 变更。

**不得把缺陷抬高为需求变更。** 抬高会导致：清空批准信息、走一遍重批流程、在 `delivery.md` 里把自己的实现错误记成外部变更。缺陷直接修，补测试，在 `delivery.md` 说明修复内容即可。

### UI 变更 vs 技术调整

| 事实 | 分类 |
| --- | --- |
| UI 把列表项从两行改成三行 | UI 变更 |
| UI 提供了新版切图，尺寸和命名都变了 | UI 变更 |
| UI 新增了空数据态的设计 | UI 变更（原本缺失时也解除对应 `missing_ui`） |
| 决定用项目已有的公共上传组件，不新建组件 | 技术调整 |
| 决定把请求逻辑抽到统一的 api 层 | 技术调整 |
| 决定新增一个依赖来处理图片裁剪 | 技术调整（且必须暂停确认，新增依赖需授权） |

UI 变更影响的是"长什么样、怎么交互"；技术调整影响的是"用什么实现"，最终呈现不变。

### 分类速判流程

```text
收到新信息
→ 呈现或交互变了吗？          是 → UI 变更 (UCR-*)
→ 实现不符合已确认基线吗？     是 → 缺陷修复
→ 功能/规则/接口/范围/验收变了吗？ 是 → 需求变更 (CR-*)
→ 只是实现方案换了吗？         是 → 技术调整 (TECH-*)
→ 以上都不是，只补充原意       → 需求澄清 (DEC-*)
```

顺序有意义：先排除 UI 和缺陷，再判需求。因为 UI 变更和缺陷修复各有独立处理路径，误入需求变更流程会造成不必要的重批。

## 变更处理流程

### 主流程

```text
收到变化
→ 分类并生成变更编号
→ 记录原内容与新内容
→ 分析受影响和不受影响范围
→ 产品或对应负责人确认
→ 更新需求基线
→ 判断原计划是否失效
→ 更新 plan.md
→ 必要时重新批准
→ 仅实现和回归受影响部分
```

两个容易被跳过的环节：

- **"记录原内容与新内容"在确认之前。** 先把原文和新文并列写下来，再去确认。否则确认过程中原文可能被覆盖，事后无法追溯改了什么。
- **"分析不受影响范围"和"分析受影响范围"同等重要。** 只写受影响范围时，无法证明其他任务可以继续，容易演变成整体重做。

### 影响分析的 7 个维度

每次需求变更或 UI 变更都必须逐维度过一遍。写"无影响"也要写，不能省略。

| 维度 | 检查内容 |
| --- | --- |
| 1. 代码结构 | 涉及的项目、页面、组件和文件（用准确路径，标注所属项目） |
| 2. 接口 | API 请求参数、响应结构、错误状态、是否需要数据迁移或兼容旧数据 |
| 3. UI 与资源 | UI 图、切图、交互流程、响应式与适配要求 |
| 4. 横切链路 | 登录、权限、埋点、安全、跨端跳转链路 |
| 5. 工作量归属 | 已完成代码、未完成代码、需要废弃的工作 |
| 6. 验证与发布 | 测试用例、构建、联调、发布顺序 |
| 7. 估时（按需） | 开发要求估时时给出增减工时，**不自动修改原估时** |

第 7 维只在开发明确要求估时时才做。估时属于 `context.md` 的按需附录，不改 `planVersion`。给出的是"增减多少小时"，原估时保留不动，便于对照。

**影响报告示例：**

```markdown
## CR-001 影响分析

**1. 代码结构**
- 受影响：`client-app/src/pages/profile.vue`（昵称校验）、`client-app/src/api/user.js`（字段约束注释）、`admin-app/src/views/user-list.vue`（列表列宽）
- 不受影响：头像上传组件、路由配置、埋点接入

**2. 接口**
- 受影响：资料保存接口的昵称字段长度约束需后端同步放宽
- 数据迁移：无（放宽长度不影响已有数据）

**3. UI 与资源**
- 受影响：管理端列表昵称列可能溢出，需确认截断方式
- 切图：无影响

**4. 横切链路**
- 登录、权限、埋点、安全、跨端：无影响

**5. 工作量归属**
- 已完成需改：客户端表单校验（约 1 处）
- 未完成需按新规则做：管理端列表列宽与截断
- 需废弃：无

**6. 验证与发布**
- 测试用例：客户端表单校验边界用例断言改为 40；新增 41 字符超限用例
- 回归：资料保存流程
- 发布顺序：后端约束放宽需先上，否则前端放宽后保存会被后端拒绝

**7. 估时**
- 开发未要求估时，本次不输出。
```

## 不同时间点的处理

同一个变更，在不同阶段收到，处理方式不同。

### 计划批准前

**状态特征：** `stageStatus.planning` 为 `active` 或 `awaiting_confirmation`，`approvedPlanVersion` 为 `null`。

**处理：**

1. 更新 `context.md`：需求理解、已确认需求、验收标准、开放问题。
2. 追加 `CR-*` 记录到 `decisions.md`。
3. 更新 `requirementVersion`。
4. 重新生成受影响的 `plan.md` 内容，更新 `planVersion` 和 `planBasedOnRequirementVersion`。
5. 请求批准（首次批准，不是重批）。

**代价最低。** 没有已批准计划要清空，没有已写代码要废弃。`invalidatedItems` 通常不需要——`plan.md` 还没批准过，改它不构成"已有结论失效"。

例外：变更引入新的 P0 问题时，门禁一重新生效，`stageStatus.context` 退回 `blocked`、`planning` 退回 `pending`，并追加 `p0_unresolved`。

### 实现过程中

**状态特征：** `stageStatus.implementation` 为 `active`，`approvedPlanVersion == planVersion`。

**处理：**

1. 暂停受影响部分。
2. **无依赖且确定不受影响的任务可以继续。** "确定"的依据是 `plan.md` 的"技术任务及依赖"章节，不是直觉。
3. 追加 `CR-*` 记录，更新 `requirementVersion`。
4. 清空三个批准字段，`stageStatus.planning` 设为 `invalidated`。
5. 追加 `invalidatedItems`，记录受影响的实现范围。
6. 更新 `context.md` 和 `plan.md`，设新 `planVersion`，使 `planBasedOnRequirementVersion` 等于 `requirementVersion`。
7. 重新批准后实现受影响范围。
8. 删除因变更而废弃的代码和资源，在 `delivery.md` 说明哪些工作被废弃。

详细字段变化见 `recovery-scenarios.md` 场景九。

### 验证过程中

**状态特征：** `stageStatus.verification` 为 `active` 或 `awaiting_confirmation`。

**处理：**

1. 重新打开受影响的计划和实现内容：`stageStatus.planning` 设为 `invalidated`，受影响的实现范围记入 `invalidatedItems`。
2. `stageStatus.verification` 退回 `active`（或在全部验证结论都失效时设为 `invalidated`）。
3. 走一遍实现过程中的流程：更新基线、更新计划、重批、实现。
4. 完成后**重跑相关验证及必要回归**。

必要回归的判断依据：变更是否触及公共能力、路由、请求层、权限或埋点。触及了就要回归，没触及只跑受影响模块的验证。

已通过的验证证据不删除，在 `delivery.md` 中标注为"变更前的验证结果"，新一轮证据独立记录。**不得**把变更前的通过结果当作变更后的验证依据。

### 已交付后

**状态特征：** `targetStage` 对应阶段为 `complete`，全局 `status` 为 `complete`。

**处理的第一步是询问开发**：

```text
本次变更在需求 feature-001 已交付后收到。

请确认处理方式：
A. 创建新需求 — 使用新的需求标识和新的 5 文件目录，原需求产物不动
B. 沿用原需求标识 — 在原 delivery.md 追加以变更编号命名的独立交付批次

建议：<给出建议及理由，例如变更范围较大且与原需求可独立验收，建议 A>
```

**不自动决定。** 这个选择影响产物组织方式、后续追溯路径和交付批次划分，属于开发的组织决策。

| 选项 | 做法 |
| --- | --- |
| A 创建新需求 | 新的 `requirementId`，新的产物目录和 5 个文件；在新 `context.md` 注明来源于原需求的变更；原需求产物完全不动 |
| B 沿用原需求 | 在原 `delivery.md` 追加以变更编号命名的独立交付批次；**禁止修改旧批次内容**；`workflow-state.json` 的阶段状态按变更重新推进 |

选 B 时，`workflow-state.json` 的处理：更新 `requirementVersion`，清空批准字段，`stageStatus` 中受影响阶段退回相应状态（`planning` → `invalidated`，`verification` / `delivery` → `pending` 或 `active`），追加 `invalidatedItems`。原有的 `decisions.md` 记录一条不改，只追加。

选建议的参考：变更小且与原需求同一验收范围 → B；变更引入独立功能点、需要单独排期或单独验收 → A。

## 状态与门禁规则

### 变更确认后的字段动作

| 动作 | 条件 | 说明 |
| --- | --- | --- |
| 更新 `requirementVersion` | 变更确认后，始终执行 | 用变更确认时间；需求系统有原始版本号时优先记录原始版本号 |
| `planBasedOnRequirementVersion` 保持旧值 | 直到 `plan.md` 真的更新完 | 两者不等 = "计划已过期，不得实现受影响部分"的判断依据 |
| 清空 `approvedPlanVersion` / `approvedAt` / `approvedByRole` | 变更影响已批准计划时 | 三个字段同时清空，不允许只清一个 |
| `stageStatus.planning` 设为 `invalidated` | 变更影响已批准计划时 | 已批准的计划整体不再有效 |
| 追加 `invalidatedItems` | 存在局部失效范围时 | 每个失效范围一条，带 `changeId` |
| 某阶段 `stageStatus` 设为 `invalidated` | 该阶段**全部**已有结论都失效时 | 局部失效不设，只记 `invalidatedItems` |
| 未受影响阶段和任务状态**不变** | 始终 | 不因为有变更就把所有阶段重置 |

### 两条硬门禁

1. **`planBasedOnRequirementVersion != requirementVersion` 时，不得实现受影响的变更。** 先更新 `plan.md`。
2. **`approvedPlanVersion != planVersion` 时，不得修改业务代码。** 先走门禁二重批。

`approvedPlanVersion` 为 `null` 属于第二条不成立。

### 更新计划时的字段动作

```text
更新 plan.md 内容
→ 设置新的 planVersion
→ 使 planBasedOnRequirementVersion == requirementVersion
→ 请求重新批准
→ 批准后：approvedPlanVersion = 当前 planVersion，记录 approvedAt 和 approvedByRole
→ stageStatus.planning 从 invalidated 恢复为 complete
→ Skill 自动清理已恢复的 invalidatedItems 条目
```

**只重新分析和验证受影响范围，不从头重做无关阶段。** 一个昵称长度的变更不需要重新做项目画像分析。

### 变更必须先记录

紧急或口头变更也必须记录。**未记录前不能作为稳定需求基线。**

含义：没有 `CR-*` 记录的变更，不能用来更新 `requirementVersion`，不能作为实现依据，不能写进 `plan.md` 的已确认内容。

## 紧急与口头变更的边界

口头或紧急变更常见于电话、会议、即时消息中的临时口径。处理规则如下。

### 记录位置

| 内容状态 | 写哪里 |
| --- | --- |
| 未获书面确认 | `context.md` 的开放问题，标注"待确认"和信息来源 |
| 已获书面确认 | 追加到 `decisions.md`（`CR-*` 或 `DEC-*`） |

**未确认内容不进 `decisions.md`。** `decisions.md` 是已确认结论的追加式记录，混入未确认内容会让后续实现把假设当基线。

`context.md` 开放问题的记录格式：

```markdown
| ID | 优先级 | 问题 | 信息来源 | 当前口径 | 是否已授权临时实现 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| ORAL-01 | P1 | 昵称长度上限是否放宽到 40？ | 会议口头，开发转述，未书面确认 | 暂按 40 | 是（开发授权，见 DEV-003） | 待书面确认 |
```

### 是否允许基于临时假设继续开发

分三种情况，边界严格。

**情况 1：涉及安全、资金、权限、隐私或数据写入的 P0 内容 — 不允许**

不允许基于临时假设开发，等待正式确认。即使开发授权也不允许。

判断范围：

| 领域 | 举例 |
| --- | --- |
| 安全 | 认证方式、令牌处理、加密要求、越权防护 |
| 资金 | 金额计算、价格、优惠、退款、支付流程 |
| 权限 | 角色判断、数据可见范围、操作授权边界 |
| 隐私 | 敏感字段展示与脱敏、数据上报口径、日志内容 |
| 数据写入 | 新增、修改、删除业务数据，尤其不可逆的删除和批量操作 |

理由：这类内容错了的后果不可通过"改回来"消除。资金算错会产生真实损失；权限放宽会产生已发生的数据暴露；错误删除的数据可能无法恢复。

处理：追加 `p0_unresolved` 阻塞项（`scope` 为具体问题 ID），暂停该范围，等正式确认。

**情况 2：其他内容 — 需开发明确授权**

只有开发明确授权"按临时方案实现"后才可继续。

- 授权必须明确，不是默认。开发说"你先看着办"不算授权，要请其明确表态。
- **授权本身记入 `context.md`**（并可同时以 `DEV-*` 追加到 `decisions.md`，因为"开发授权临时实现"这件事本身是已确认的）。
- 记录内容：谁授权、授权范围、临时口径是什么。

**情况 3：临时实现的四条约束**

无论哪种授权，临时实现都必须满足：

| 约束 | 具体要求 |
| --- | --- |
| 必须可回退 | 在 `context.md` 记录改动范围（准确文件路径）和回退方式 |
| 不得交付 | 任何临时实现都不得进入交付批次 |
| 不得部署 | 任何临时实现都不得部署或发布 |
| 有时限 | 超过一个工作日未确认时，暂停相关实现 |

`context.md` 的临时实现记录格式：

```markdown
## 临时实现（待确认后转正或回退）

### ORAL-01 昵称长度暂按 40

- **授权：** 开发明确授权按临时方案实现（见 decisions.md DEV-003）
- **改动范围：**
  - `client-app/src/pages/profile.vue`：校验上限常量 20 → 40
  - `client-app/src/pages/__tests__/profile.spec.js`：边界用例断言同步调整
- **回退方式：** 将上述两处常量与断言改回 20，无其他关联改动
- **开始时间：** 2026-08-13T16:00:00+08:00
- **确认时限：** 2026-08-14T16:00:00+08:00（超时暂停相关实现）
- **交付状态：** 不得交付、不得部署
```

超时处理：到时限仍未获书面确认时，暂停相关实现，向开发报告。由开发决定是回退还是继续等待。继续等待需要重新授权并记录新的时限。

### 紧急变更处理速查

```text
收到口头/紧急变更
→ 写入 context.md 开放问题，标注来源与"待确认"
→ 涉及安全/资金/权限/隐私/数据写入的 P0？
    是 → 追加 p0_unresolved，暂停该范围，等正式确认（不可授权绕过）
    否 → 开发明确授权"按临时方案实现"？
            否 → 暂停该范围，等授权或等确认
            是 → 记录授权 + 改动范围 + 回退方式 + 一个工作日时限
                 → 可继续实现，但不得交付、不得部署
                 → 超时未确认 → 暂停
→ 获得书面确认后
    → 追加 CR-*（或 DEC-*）到 decisions.md
    → 更新 requirementVersion
    → 更新 plan.md 并按门禁二重批
    → 从 context.md 临时实现章节移除该条，转为正式实现
```

## 批量变更处理

多个变更同时到达时（例如产品一次性给出 5 条调整），按以下规则处理。

### 1. 每个变更独立记录，不合并

5 条调整 → 5 个 `CR-*` 记录。每条各自记录原内容、新内容、来源、影响范围。

理由：合并成一条会失去逐条追溯能力。后续某一条被回滚或再次调整时，无法定位对应记录；产品对其中一条改主意时，也无法单独处理。

### 2. 先合并去重影响范围，再生成统一影响报告

记录独立，但影响分析要合起来做：

```text
CR-001 影响：profile.vue、user.js、user-list.vue
CR-002 影响：profile.vue、avatar-upload.vue
CR-003 影响：user.js
        ↓ 合并去重
统一影响范围：profile.vue、user.js、user-list.vue、avatar-upload.vue
```

生成一份统一影响报告，按 7 个维度组织，每个受影响项标注是哪些变更导致的：

```markdown
## 批量变更影响报告（CR-001 / CR-002 / CR-003）

**1. 代码结构**

| 文件 | 关联变更 | 影响内容 |
| --- | --- | --- |
| `client-app/src/pages/profile.vue` | CR-001, CR-002 | 昵称校验上限；头像上传入口位置 |
| `client-app/src/api/user.js` | CR-001, CR-003 | 昵称字段约束；新增手机号字段 |
| `client-app/src/components/avatar-upload.vue` | CR-002 | 上传尺寸限制 |
| `admin-app/src/views/user-list.vue` | CR-001 | 昵称列宽与截断 |

不受影响：路由配置、埋点接入、登录流程
```

理由：分别出 3 份影响报告会让同一个文件被列 3 次，开发难以判断总体改动面，也容易漏掉变更之间的相互作用。一份统一报告只生成一次 `plan.md` 更新和一次重批。

### 3. 按优先级排序

统一影响报告中给出实施顺序，排序依据：

| 优先级 | 类型 |
| --- | --- |
| 高 | 阻塞其他变更的前置变更；涉及安全、权限、资金的变更 |
| 中 | 影响多个文件或跨项目的变更 |
| 低 | 局部、独立、影响面小的变更 |

排序是建议，最终顺序由开发确认。

### 4. 变更间有依赖或冲突时先问开发

**依赖示例：** `CR-002` 要求头像上传入口移到新的操作区，而 `CR-004` 要求删除该操作区。必须先确认最终形态，否则实现顺序不同结果不同。

**冲突示例：** `CR-001` 要求昵称上限 40，`CR-005` 要求昵称上限 30。两条互斥。

处理：**不自行推断哪个更新、哪个优先。** 把冲突或依赖关系写入 `context.md` 开放问题，列出各选项及影响，询问开发。

```markdown
| ID | 优先级 | 问题 | 冲突内容 | 影响范围 | 建议选项 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| CONF-01 | P0 | 昵称长度上限最终取值？ | CR-001 要求 40，CR-005 要求 30 | 表单校验、接口约束、列表展示、测试断言 | A 取 40（CR-001 较晚） / B 取 30（CR-005 较晚） / C 由产品重新裁决 | 待确认 |
```

即使能从时间戳看出哪个更晚，也要确认——后到的不一定是最终结论，可能是不同人各说一句。

### 5. 一次重批

批量变更走一次统一的 `plan.md` 更新和一次门禁二重批。不为每个变更单独重批。

`planVersion` 更新一次，`decisions.md` 里的 `DEV-*` 批准记录中列出本次批准覆盖了哪些变更编号。

## 变更回滚

变更确认并实现后，产品又要求撤回。

### 两个基本规则

1. **不删除变更记录。** `decisions.md` 是追加式的，历史决定不静默修改。
2. **追加回滚决策。** 新增一条记录，通过"替代决策"字段引用被回滚的变更。

### 两种情况

**情况 A：回滚到上一稳定版本**

即"撤回这个变更，恢复变更前的行为"。

```markdown
## [CR-006] 2026-08-15 10:00 需求变更（回滚 CR-001）

**原内容：** 用户昵称最长 40 个字符（CR-001 引入）。

**新内容：** 恢复为最长 20 个字符。

**变更来源：** 产品回复，由开发转述。

**回滚类型：** 回滚到上一稳定版本。

**影响项目：** 用户端、管理端。

**受影响：** 表单校验、接口字段约束、列表展示和测试用例（即 CR-001 的全部影响范围）。

**不受影响：** 头像上传和页面基础布局。

**处理结论：** 撤销 CR-001 的代码改动，恢复变更前实现；重跑 CR-001 影响范围的验证。

**需求版本：** 2026-08-15T10:00:00+08:00。

**替代决策：** 替代 CR-001。
```

处理要点：

- 受影响范围直接复用被回滚变更的影响分析，不重新推导（除非该变更实现过程中发现了额外影响）。
- **`requirementVersion` 前进，不回退。** 回滚是一次新的基线变化，时间只向前。
- 回滚后必须重跑该范围的验证。不能因为"恢复到之前的样子"就复用变更前的验证证据——中间还有其他变更，代码状态已不同。
- 后端已配合改过约束时，回滚需要与后端同步，写入影响分析的"发布顺序"维度。

**情况 B：修正变更内容**

即"变更方向对，但具体值或细节错了"。

```markdown
## [CR-007] 2026-08-15 11:00 需求变更（修正 CR-001）

**原内容：** 用户昵称最长 40 个字符（CR-001 引入）。

**新内容：** 用户昵称最长 32 个字符。

**变更来源：** 产品回复，由开发转述。

**回滚类型：** 修正变更内容，不回滚到变更前状态。

**影响项目：** 用户端、管理端。

**受影响：** 表单校验上限值、接口字段约束、测试边界断言。

**不受影响：** 列表列宽（32 与 40 的展示处理一致）、头像上传、页面布局。

**处理结论：** 在 CR-001 基础上调整数值；仅重跑边界值相关用例。

**需求版本：** 2026-08-15T11:00:00+08:00。

**替代决策：** 修正 CR-001，不撤销其结构性改动。
```

处理要点：

- 影响范围通常**小于**被修正的变更。CR-001 引入了列宽调整，CR-007 只改数值，列宽不用再动。
- 需要重新做影响分析，不能直接复用——修正后的影响面和原变更不同。
- 重跑范围比情况 A 小，只跑真正受影响的用例。

### 区分标准

> **问：撤回后，代码是回到变更前的形态，还是保留变更引入的结构、只调整内容？**
>
> - 回到变更前形态 → 情况 A，复用原影响分析，全范围重跑
> - 保留结构、调整内容 → 情况 B，重做影响分析，按实际范围重跑

### 已交付内容的回滚

已交付后要求回滚时，先按"已交付后"规则询问开发是创建新需求还是沿用原需求标识。回滚不因为"是撤回操作"就跳过这个询问。

回滚涉及已部署内容时，部署和发布仍需开发单独授权。Skill 不自动执行任何部署或回滚发布操作。

## 变更编号规则

### 五个前缀

| 前缀 | 用途 | 确认方 |
| --- | --- | --- |
| `DEC-*` | 产品确认（含需求澄清） | 产品或有决策权限的负责人 |
| `DEV-*` | 开发确认（含计划批准、技术选择、风险接受、临时实现授权） | 开发 |
| `CR-*` | 需求变更 | 产品 |
| `UCR-*` | UI 变更 | UI 或产品 |
| `TECH-*` | 技术调整 | 开发 |

### 编号规则

- **三位数，从 001 起。** `DEC-001`、`CR-001`、`UCR-001`、`TECH-001`、`DEV-001`。
- **单个需求内唯一。** 同一 `requirementId` 下，同一前缀的编号不重复。
- **各前缀独立计数。** `DEC-001` 和 `CR-001` 可以共存，它们是不同序列。
- **只增不减。** 记录被回滚或推翻时，编号不回收、不复用。回滚用新编号并在"替代决策"里引用旧编号。
- **超过 999 时不改格式**，继续用 `CR-1000`。单个需求达到这个量级说明需求拆分有问题，值得向开发提出。

### 编号示例

一个需求的 `decisions.md` 可能是这样的序列：

```text
DEC-001  产品确认：未登录不可访问资料页
DEC-002  产品确认：删除操作需二次确认
DEV-001  开发确认：批准 plan.md（版本 2026-08-13T10:00:00+08:00）
TECH-001 技术调整：复用已有 common-upload 组件
DEV-002  开发确认：批准 plan.md（版本 2026-08-13T11:00:00+08:00）
CR-001   需求变更：昵称上限 20 → 40
DEV-003  开发确认：授权 ORAL-01 按临时方案实现
UCR-001  UI 变更：管理端列表昵称列改为单行截断
DEV-004  开发确认：批准 plan.md（版本 2026-08-14T09:00:00+08:00）
CR-002   需求变更：新增手机号展示
```

`DEV-*` 出现频繁是正常的——每次计划批准都是一条开发确认。

### 编号引用

- `invalidatedItems.changeId` 必须是一个真实存在的编号。
- `context.md` 的开放问题解决后，在状态列引用对应编号，如"已确认，见 DEC-003"。
- `delivery.md` 的交付批次用变更编号命名，如 `## Delivery CR-001 / 2026-08-14`。
- 回滚记录的"替代决策"字段引用被回滚编号。

## 决策记录格式

### 需求变更（`CR-*`）

```markdown
## [CR-001] 2026-08-13 15:00 需求变更

**原内容：** 用户昵称最长20个字符。

**新内容：** 用户昵称最长40个字符。

**变更来源：** 产品回复，由开发转述。

**影响项目：** 用户端、管理端。

**受影响：** 表单校验、接口字段约束、列表展示和测试用例。

**不受影响：** 头像上传和页面基础布局。

**处理结论：** 更新计划并重新批准后实现。

**需求版本：** 2026-08-13T15:00:00+08:00。
```

字段说明：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 标题行 | 是 | `[编号] 日期 时间 类型` |
| 原内容 | 是 | 变更前的准确表述，不用"原来的逻辑"这类模糊说法 |
| 新内容 | 是 | 变更后的准确表述 |
| 变更来源 | 是 | 谁提出、通过什么途径。转述时写明"由开发转述"。未提供姓名时只记角色，不虚构姓名 |
| 影响项目 | 是 | 多项目时逐个列出；单项目写项目名 |
| 受影响 | 是 | 影响分析 7 个维度的结论摘要 |
| 不受影响 | 是 | 明确写出，用于证明其他任务可继续 |
| 处理结论 | 是 | 下一步做什么，是否需要重批 |
| 需求版本 | 是 | 新的 `requirementVersion` 值 |
| 替代决策 | 回滚或推翻时必填 | 引用被替代的编号；无则写"无" |

### 产品确认（`DEC-*`）

```markdown
## [DEC-001] 2026-08-13 14:30 产品确认

**关联问题：** PRD-01

**问题：** 用户资料页面是否允许未登录访问？

**决策：** 不允许，未登录用户进入登录页。

**确认来源：** 产品回复，由开发转述。

**影响：** 路由权限、接口调用时机和测试用例。

**替代决策：** 无。
```

### UI 变更（`UCR-*`）

```markdown
## [UCR-001] 2026-08-14 09:00 UI 变更

**原内容：** 管理端用户列表昵称列两行展示，超出换行。

**新内容：** 单行展示，超出末尾省略号截断，悬浮显示完整内容。

**变更来源：** UI 提供新版页面图（文件名与更新时间：user-list-v2，2026-08-14）。

**影响项目：** 管理端。

**受影响：** 列表列样式、行高、悬浮提示组件、视觉验证项。

**不受影响：** 列表数据接口、分页、筛选逻辑。

**切图变化：** 无新增切图。

**处理结论：** 更新 plan.md 的 UI 与资源映射及文件清单，重新批准后实现；补充视觉对比验证。

**替代决策：** 无。
```

UI 变更记录额外要写"切图变化"，因为切图的增删改会影响资源映射和文件清单。

### 技术调整（`TECH-*`）

```markdown
## [TECH-001] 2026-08-13 15:10 技术调整

**原方案：** 新建 avatar-upload 组件。

**新方案：** 复用已有 common-upload 组件，通过参数配置裁剪比例。

**调整来源：** 开发反馈。

**需求是否变化：** 否。

**影响项目：** 用户端。

**受影响：** 文件清单（减少 1 个新建文件）、组件测试范围。

**不受影响：** 需求验收标准、接口对接、UI 还原效果。

**处理结论：** 更新 plan.md 并重新批准；验收标准不变。

**替代决策：** 无。
```

技术调整记录必须明确写"需求是否变化：否"。如果发现需求实际会变，那它不是技术调整，应改为 `CR-*`。

### 沿用原需求标识时的交付批次

已交付后选择沿用原需求标识时，在原 `delivery.md` 追加：

```markdown
## Delivery CR-001 / 2026-08-14

### 变更范围

- 关联变更：CR-001
- 计划版本：2026-08-14T09:00:00+08:00（批准记录见 decisions.md DEV-004）
- 改动文件：
  - `client-app/src/pages/profile.vue`（修改）
  - `client-app/src/api/user.js`（修改）
  - `admin-app/src/views/user-list.vue`（修改）
- 废弃工作：无

### 验证证据

- 执行的命令、结果、失败数量（本次运行的真实输出）
- 回归范围及结论
- 人工验证项及执行状态

### 未验证项与风险

- 未执行的验证及原因
- 已知风险和遗留事项
- 对旧功能的影响
```

规则：

- 批次标题用变更编号命名，加交付日期。
- **禁止修改旧批次内容。** 只追加新批次。旧批次的验证证据是当时的事实，不因后续变更而失效或需要更新。
- 每个批次的验证证据必须是**本批次运行**的结果，不复用之前批次的输出。
- 多个变更合并交付时，标题可列多个编号：`## Delivery CR-001 + CR-002 / 2026-08-15`。

## 常见误判纠正

### 误判 1：把需求变更当需求澄清

❌ **错误：** 产品说"昵称上限改成 40"，当成澄清，直接改代码，只在 `context.md` 补一句。

✅ **正确：** 这是需求变更。三项检验全部命中：验收标准要改、已写代码要动、测试断言要改。必须建 `CR-*`、更新 `requirementVersion`、清空批准、更新 `plan.md`、重批。

### 误判 2：把需求澄清抬成需求变更

❌ **错误：** 产品说"中文按 1 个字符计"，建 `CR-*`，清空批准信息，走完整重批流程。

✅ **正确：** 原需求已含"支持中英文"，这只是补充计数口径。如果代码本来就按字符计，什么都不用改——更新 `context.md`、追加 `DEC-*`，计划未受影响不重批。

### 误判 3：把自己的实现错误记成需求变更

❌ **错误：** 已确认需求写"昵称最长 20"，实现里写了 50，发现后建 `CR-001` 说"需求变更为 20"。

✅ **正确：** 这是缺陷修复。基线一直是 20，实现偏离了基线。直接改回 20，补边界测试，在 `delivery.md` 说明修复内容。不清空批准，不更新 `requirementVersion`。

### 误判 4：口头变更直接进 `decisions.md`

❌ **错误：** 会议上产品口头说了个新口径，立刻追加 `CR-002` 到 `decisions.md`，更新 `requirementVersion`。

✅ **正确：** 未获书面确认的内容写 `context.md` 开放问题，标注来源和"待确认"。书面确认后才进 `decisions.md`。未记录的变更不能作为稳定需求基线。

### 误判 5：安全类内容也按临时假设开发

❌ **错误：** 口头说"权限先放开，都能看"，开发说"你先按这个做"，于是实现了放开权限的版本。

✅ **正确：** 权限属于 P0 禁止清单（安全、资金、权限、隐私、数据写入）。**即使开发授权也不允许**基于临时假设开发。追加 `p0_unresolved`，暂停该范围，等正式确认。这类内容错了的后果不能通过"改回来"消除。

### 误判 6：临时实现进了交付

❌ **错误：** 临时方案实现完，验证通过，写进 `delivery.md` 的交付内容。

✅ **正确：** 任何临时实现都不得交付、不得部署。它停留在"已实现待确认"状态，记在 `context.md` 的临时实现章节，带改动范围和回退方式。书面确认后转正才能交付。

### 误判 7：批量变更合并成一条记录

❌ **错误：** 产品一次给 5 条调整，写成一条 `CR-003` 包含全部 5 项。

✅ **正确：** 5 条独立记录，5 个编号。合并会失去逐条追溯能力。但影响范围要**合并去重**后生成一份统一影响报告，并走一次重批。

### 误判 8：批量变更逐条重批

❌ **错误：** 5 个变更，更新 `plan.md` 5 次，请求批准 5 次。

✅ **正确：** 记录独立，影响分析合并，`plan.md` 更新一次，`planVersion` 更新一次，重批一次。`DEV-*` 批准记录里列出覆盖了哪些变更编号。

### 误判 9：变更冲突时自行按时间取新的

❌ **错误：** `CR-001` 说 40，`CR-005` 说 30，`CR-005` 时间更晚，就按 30 实现。

✅ **正确：** 写入 `context.md` 开放问题，列出各选项和影响，询问开发。后到的不一定是最终结论，可能是不同人各说一句。

### 误判 10：回滚时删除原变更记录

❌ **错误：** `CR-001` 被撤回，把 `decisions.md` 里的 `CR-001` 删掉，或改成"已撤销"。

✅ **正确：** `decisions.md` 追加式，历史不静默修改。新增回滚记录（如 `CR-006`），在"替代决策"里写"替代 CR-001"。`CR-001` 原文一字不改。

### 误判 11：回滚时把 `requirementVersion` 改回旧值

❌ **错误：** 回滚 `CR-001`，把 `requirementVersion` 恢复成 `CR-001` 之前的值。

✅ **正确：** `requirementVersion` 只向前。回滚是一次新的基线变化，用回滚确认时间作为新版本。改回旧值会让版本比较逻辑失效。

### 误判 12：回滚后复用变更前的验证证据

❌ **错误：** "反正恢复到 `CR-001` 之前的样子了"，直接引用变更前那轮的测试结果。

✅ **正确：** 中间还有其他变更，代码状态已不同。必须重跑该范围的验证，记录本次运行的真实证据。

### 误判 13：已交付后自动决定处理方式

❌ **错误：** 已交付后收到变更，自动创建新需求标识和新目录。

✅ **正确：** **询问开发**是创建新需求还是沿用原需求标识，给出建议和理由，等开发选择。这个选择影响产物组织和追溯路径，属于开发的组织决策。

### 误判 14：修改旧交付批次

❌ **错误：** 沿用原需求标识时，把 `CR-001` 的改动直接写进原来那个交付批次。

✅ **正确：** 追加以变更编号命名的独立批次，禁止修改旧批次内容。旧批次的验证证据是当时的事实。

### 误判 15：变更时把所有阶段重置

❌ **错误：** 收到一个昵称长度变更，把 `planning`、`implementation`、`verification` 全设为 `invalidated`，从头重做包括项目画像分析。

✅ **正确：** 先做影响分析。`planning` 因批准失效设为 `invalidated`；实现的局部失效只记 `invalidatedItems`；`context` 阶段的项目画像与本变更无关，保持 `complete`。只重做受影响范围。

### 误判 16：变更确认时同步改 `planBasedOnRequirementVersion`

❌ **错误：** 更新 `requirementVersion` 的同时把 `planBasedOnRequirementVersion` 也改成新值。

✅ **正确：** 保持旧值直到 `plan.md` 真的更新完。两者不等正是"计划已过期，不得实现受影响部分"的判断依据。提前改掉会让这道保护失效。

---

## 总结

**分类先于处理：**

1. 呈现或交互变了 → UI 变更
2. 实现不符基线 → 缺陷修复
3. 功能/规则/接口/范围/验收变了 → 需求变更
4. 只换实现方案 → 技术调整
5. 只补原意 → 需求澄清

**判断技巧：**

- 区分澄清和变更：**"原需求的文字隐含这个结论吗？"** 隐含 → 澄清。三项检验（验收标准要改吗、已写代码要动吗、测试断言要改吗）任一命中 → 变更。判不准时按变更处理，代价更小。
- 区分变更和缺陷：**"拿基线对照实现，是谁错了？"** 实现错了 → 缺陷。基线要改 → 变更。
- 决定能否基于临时假设开发：**"错了能改回来吗？"** 安全、资金、权限、隐私、数据写入 → 不能，等正式确认，授权也不行。其他 → 需开发明确授权、可回退、不交付、一个工作日时限。
- 处理批量变更：**"记录分开，影响合并，重批一次。"**
- 处理回滚：**"回到变更前形态，还是保留结构改内容？"** 前者复用原影响分析全范围重跑；后者重做影响分析按实际范围重跑。记录只追加，版本只前进。
