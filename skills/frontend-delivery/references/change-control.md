# 变化分类与处理

按已确认基线判断变化，不能用“改了代码或测试”定义需求变更。
任务版本、批准及失效字段见 state-machine.md；确认方式见 workflow-gates.md。

## 分类顺序

先判断是否恢复已确认预期：
- 缺陷修复：原规则不变，实现偏离预期。视觉实现偏离已确认设计也属于缺陷。
- 需求变更：目标、范围、业务规则、验收行为或职责改变。
- UI 变更：业务规则不变，已确认视觉或交互设计改变。
- 技术调整：需求及设计不变，实现方式、依赖或文件范围改变。
- 需求澄清：补充表达或确认已有含义，不改变已有规则。

一个变化可涉及多类，记录主要类型和实际影响，不强迫归入错误类别。
没有确认基线时先识别未知输入，不声称对旧需求做了变更。
澄清也可能推翻此前假设，因此仍需检查计划、实现和证据是否受影响；分类不免除影响分析。

## 处理步骤

1. 对比来源与现有基线，区分已确认变化和待确认建议。
2. 检查受影响验收项、项目、UI、接口、任务、共享调用方、依赖及验证证据。
3. 有业务选择时说明差异和取舍；明确用户指令已有授权时直接记录，不重复确认。
4. 更新事实和计划的受影响部分，按需要重新取得相关任务批准。
5. 完成必要实现和验证，再逐阶段解除失效并更新交付结果。

小改动用对话保持最少记录，常规需求更新当前清单或 task.md；完整流程需要追溯重要决定、批准或范围变化时使用 decisions.md，已启用 workflow-state.json 时同步相应状态索引。
未确认关键变化记开放问题和范围级阻塞；已经确认但产出过期记 invalidatedItems，两者有不同原因时可并存。
影响未隔离前保护可能受影响范围；有证据证明独立的工作继续推进，不全量重置。
Figma 节点重新读取后发生变化时，先依据用户要求及来源约定判断是否纳入本次基线。明确属于下一版或范围外草稿的变化不影响本次批准；归属未定且影响本次目标时记问题和范围级阻塞，不直接替换基线。确认纳入后，再按实际结构、标注、变量、资源、截图或动效差异更新相关计划、任务版本、批准和证据；不能因文件级时间变化全量返工。

## 版本与记录

需求基线真正改变才更新 requirementVersion；计划可执行内容改变更新 planVersion，taskVersion 是否递增按 state-machine.md 的批准边界判断，不随 planVersion 同步递增。
planBasedOnRequirementVersion 在计划已核对新基线后更新，不能随收到变更提前更新。
只有进度、估时或说明文字改变时不更新可执行版本。
旧批准对版本已变任务失效，未变化任务保留；原本已批准范围内且不改变约定的实现缺陷修正或细节调整无需重批，仍须重新核对受影响实现和验证证据。
任务批准不代表代码已修复，也不使旧验证证据重新有效。

完整流程使用稳定、递增、不复用的记录 ID：
- DEC-*：需求澄清、业务决定及批准。
- CR-*：需求变更。
- UCR-*：UI 变更。
- TECH-*：技术调整。
- FIX-*：需要追溯的缺陷修复；普通局部修正不强制单独建记录。
保留原有记录前缀和历史引用，不为统一格式重编号。

记录包含来源、实际确认时间、确认角色、原结论与新结论、影响及不受影响范围、相关任务版本、处理决定。
同一次回复明确处理多个独立变更时可一起评估和一次批准，但每个变更保留可追溯身份。
相互冲突时不能按时间自动取最新；由规则优先级或用户确定适用结论。
临时方案只有在明确授权、低风险且范围清楚时才可执行；记录限制和退出条件，未转正不能算正式验收完成。

## 回滚与交付后变化

回滚作为当前的一次新变化记录，保留原记录和新版本，不把版本倒退成历史值。
重新核对当前依赖、接口、数据状态及授权；曾经可运行的旧实现不保证现在可用，历史证据不能替代当前验证。
只移除本次确已废弃且允许处理的改动，不覆盖他人工作。Git 回滚、部署或真实数据操作仍遵守操作权限。
交付后修改沿用需求并追加批次，还是新建需求，按工作连续性和用户要求决定；不为小修复强制新建全套文档。
