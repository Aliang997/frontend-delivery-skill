# UI 分析与技术计划

仅在需要方案时加载。小改动无需生成计划；常规需求用简短任务清单；完整流程使用 plan.md。
任务字段、版本和批准索引统一见 state-machine.md，授权见 workflow-gates.md。

## UI 依据

先判断任务是否需要新的视觉或交互决策，不能按“新增页面”或“Bug 修复”标签一刀切。
可用来源包括 Figma 节点、本地图片或截图、明确文字要求、用户指定或项目已认可的同类页面；没有 uiDir 不等于没有依据。
要求按图片、截图或 Figma 设计还原，或来源包含明确动效时，读取 ui-restoration.md，按来源入口执行还原和对比闭环。Figma 任务可能跨会话或经历外部等待时，在当前任务记录或计划中保留该文件要求的来源基线。本文件只维护通用 UI 依据与计划内容，不复制工具步骤。
已有通用加载、空态或错误提示可以沿用，记录来源即可。关键行为不清楚、来源冲突或无法确定目标设计时，才按受影响页面或任务记录 missing_ui。
纯逻辑修改通常不需要设计资料；视觉缺陷修复仍需可核对的预期效果。
缺少局部设计不妨碍独立逻辑、已确定页面或计划草案继续推进。

不是还原任务时，读取确实涉及的图和资源，记录页面/状态、来源版本和使用位置。按需求检查：
- 布局、字号、颜色、间距与已有设计变量。
- 加载、空态、错误、禁用及交互反馈。
- 响应式、滚动、吸顶吸底、安全区、键盘遮挡。
- 图片用途、尺寸比例、透明背景、清晰度与资源是否重复或缺失。

有清晰依据时按现有约定实现，不为每个像素请求确认；不能查看设计时说明限制，不声称已完成视觉核对。
资源路径、名称大小写和换行编码规则见 SKILL.md，不把本机绝对路径写入业务资源引用。

## 计划内容

常规任务只保留目标、相关文件、主要动作、验证方式及真正待确认点。
完整计划按需包含：
- 目标、验收项引用、范围与明确排除项。
- UI/资源来源和映射；不涉及时标不适用。
- 需创建或修改的文件及所属项目、改动用途。
- 必要的数据流、页面状态、异常和跨端处理。
- API 清单与确认来源；具体检查见 implementation-and-api.md。
- 稳定任务 ID、版本、前置任务、验收项、验证项及进度。
- 不允许修改的范围、缺失输入和外部依赖的引用。

每个任务应能独立判断前提、批准范围、完成条件。不要按每个微小编辑拆任务，也不要把所有项目装进一个无法局部批准的任务。
依赖写准确任务 ID，无依赖明确写无。跨项目契约或共享能力也是依赖；发现循环先拆分或解决前提。
任务的定义和进度只在一个位置维护，文件清单、估时及交付结果引用相同任务 ID，不能各自建立另一套任务。
估时只在用户需要时提供，注明假设和等待依赖；估时变化不触发任务重批。

## 接口与技术选择

契约未确认时只列业务需要、待确认字段和对应阻塞，不编造地址、方法、错误码。
已有规范与安全可用实现足够时直接沿用；只有影响范围、依赖、技术路线存在实质取舍才提交方案。
新增依赖先说明必要性、项目及替代方案，安装和依赖清单修改遵守用户与项目权限，不把批准计划当作安装许可。
不为计划完整而增加未要求的重构、通用层或新测试框架。

## 验证方案

按 frontend-risk-checks.md 的场景索引选取与本次行为相关的章节，将实际风险关联到已有验收项、任务和验证项，不复制整份检查表。
项目已有代码评审、CI 或发布要求影响交付时，按 testing-and-delivery.md 的“衔接项目工程流程”确认适用阶段、必要条件与执行者，纳入当前计划；不等待实现结束才识别必要门禁。
每个必要验证项使用 V-* ID，关联验收项和任务，写清操作或实际命令、通过标准、目标端、所需环境及执行者。
按改动风险选择静态检查、已有自动化或人工核对；权限禁止的命令留给用户，不自行执行。
缺少工具、账号、真机或服务时写可行替代方案及无法覆盖部分。不得用静态检查替代行为验证后声称等价。
公共能力变化才按调用方扩大必要回归；小改动不固定跑完整验证。
草案可带未决部分交付；可执行任务的批准与依赖检查按 workflow-gates.md 执行。
