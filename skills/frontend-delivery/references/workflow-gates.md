## 人工门禁概览

frontend-delivery 有 **2 个人工门禁**：

| 门禁 | 位置 | 目的 | 通过条件 |
|------|------|------|---------|
| 门禁一 | 阶段一后 | 需求确认 | P0 问题全部解决 |
| 门禁二 | 阶段二后 | 计划批准 | P1 问题全部解决 + 开发批准计划 |

**设计原则：**
- 门禁只在关键决策点设置，不过度打断
- 门禁前必须给开发足够信息做决策
- 门禁可以暂停，支持恢复

## 问题优先级定义

### P0 - 阻塞性问题

**定义：** 不确认就无法安全实现，或可能造成业务/数据/安全错误。

**门禁规则：** 未解决时不能制定最终计划。

**判断标准：**

1. **业务规则歧义**
   - 影响核心流程的判断逻辑
   - 例：用户是否允许未登录访问？权限判断依据是什么？

2. **数据边界不清**
   - 影响数据安全或一致性
   - 例：用户数据是否包含敏感信息？是否需要脱敏？

3. **范围争议**
   - 功能是否包含在本次需求中
   - 例：是否需要支持批量操作？是否需要支持导出？

4. **接口归属不明**
   - 前后端职责划分不清
   - 例：数据校验是前端做还是后端做？重试逻辑在哪一端？

5. **安全和合规**
   - 涉及安全策略或法规要求
   - 例：用户协议是否必须勾选？敏感操作是否需要二次确认？

**示例（P0）：**

```markdown
| ID | 问题 | 为什么是 P0 |
| --- | --- | --- |
| PRD-01 | 未登录用户能否查看资料页？ | 决定权限设计和数据暴露边界，错误实现可能导致信息泄露 |
| PRD-02 | 用户删除操作是否支持撤销？ | 决定数据删除策略，无法撤销的删除需要二次确认 |
| PRD-03 | 订单金额计算是前端还是后端？ | 涉及支付安全，前端计算不可信 |
```

---

### P1 - 影响方案的问题

**定义：** 会影响技术方案、范围、接口、测试或工时，但不妨碍形成带假设的计划草案。

**门禁规则：** 未解决时不能批准计划或开始编码。

**判断标准：**

1. **技术选型**
   - 影响实现路径的技术决策
   - 例：使用哪个状态管理库？使用哪个 UI 组件库？

2. **接口细节**
   - 影响接口设计的细节
   - 例：分页参数是 page/pageSize 还是 offset/limit？

3. **交互细节**
   - 影响用户体验的交互决策
   - 例：表单提交失败后是否保留输入？加载时是否显示骨架屏？

4. **性能要求**
   - 影响实现复杂度的性能指标
   - 例：列表是否需要虚拟滚动？图片是否需要懒加载？

5. **测试范围**
   - 影响测试策略的边界
   - 例：是否需要单元测试？是否需要 E2E 测试？

**示例（P1）：**

```markdown
| ID | 问题 | 为什么是 P1 |
| --- | --- | --- |
| PRD-04 | 头像上传大小限制是多少？ | 决定前端校验规则和错误提示，但可以先给默认值 2MB |
| PRD-05 | 列表加载失败是否支持重试？ | 决定错误处理流程和交互设计 |
| PRD-06 | 是否需要支持移动端适配？ | 决定样式方案和测试范围 |
```

---

### P2 - 可给默认方案的问题

**定义：** 不影响主流程的细节，可以给出有依据的默认方案。

**门禁规则：** 在 `context.md` 记录默认方案和理由后可继续；产品否决时按需求变更处理。

**默认方案的归属：** AI 给出的默认方案是推断，不是确认。它留在 `context.md` 的开放问题里，**不进 `decisions.md`**。只有开发或产品明确表示接受后，才追加一条决策记录。沉默、未回复、未明确否决都不算接受——把推断写进决策文件会让后续所有人误以为这是拍过板的结论。

**判断标准：**

1. **文案细节**
   - 不影响功能的文案描述
   - 例：按钮文字是"提交"还是"确认"？错误提示的具体措辞？

2. **视觉细节**
   - 不影响布局的视觉调整
   - 例：按钮颜色？图标样式？

3. **边界情况**
   - 低频场景的处理方式
   - 例：用户昵称为空时显示什么？列表为空时的提示文案？

4. **便利性功能**
   - 非核心的辅助功能
   - 例：是否显示字数统计？是否支持快捷键？

**示例（P2）：**

```markdown
| ID | 问题 | 默认方案 | 理由 |
| --- | --- | --- | --- |
| PRD-07 | 保存按钮文字 | "保存" | 与项目其他页面保持一致 |
| PRD-08 | 昵称为空时显示 | "未设置昵称" | 参考类似页面的处理方式 |
| PRD-09 | 是否显示字数统计 | 显示 | 提升用户体验，实现成本低 |
```

## 门禁一：需求确认

### 触发时机

context.md 生成后，进入计划阶段前。

### 通过条件

- **必须：** 所有 P0 问题已解决
- **允许：** P1/P2 问题可以未解决

### AI 输出

```
需求分析完成，已生成：
- docs/ai-delivery/<需求标识>/context.md

产品待确认问题：
- P0: {count}个（必须解决才能制定计划）
- P1: {count}个（可以形成草案，但批准前必须解决）
- P2: {count}个（已给出默认方案）

请转发产品待确认问题给产品，并将产品回复告诉我。

P0 必须获得产品或有决策权限的负责人明确确认。
开发只能转述确认结果，不能用默认方案代替确认。
```

### 开发回复处理

**情况 1：产品确认回复**

开发转述产品回复：
```
产品回复：
PRD-01: A，必须登录
PRD-02: B，支持撤销
```

AI 动作：
1. 更新 context.md 的问题状态列
2. 追加到 decisions.md：
   ```markdown
   ## [DEC-001] 2026-08-13 14:30 产品确认
   
   **关联问题：** PRD-01
   
   **问题：** 未登录用户能否查看资料页？
   
   **决策：** A，必须登录。
   
   **确认来源：** 产品回复，由开发转述。
   
   **影响：** 路由权限、接口调用时机和测试用例。
   
   **替代决策：** 无。
   ```
3. 清除对应的 P0 阻塞项
4. 如果所有 P0 已解决，继续下一阶段

**情况 2：开发要求跳过 P0 确认**

开发说：
```
P0 问题都可以按默认方案，继续。
```

AI 动作：
1. 不接受。P0 的定义是不能猜、不能错，没有可直接采用的默认答案。
2. 说明每个未确认 P0 的具体风险（数据错误、安全边界、业务规则），以及错误实现的后果。
3. 保留 `p0_unresolved` 阻塞项，`stageStatus.context` 保持 `blocked`。
4. 如果开发本人具备该问题的决策权限，请其以决策者身份明确回答，按情况 1 记录并注明确认角色为开发。
5. 其余情况等待产品或负责人确认。

**情况 3：需求变更**

开发说：
```
产品说需求改了，现在要支持未登录访问。
```

AI 动作：
1. 执行需求变更流程（见 SKILL.md "需求变更处理"章节）
2. 更新 context.md
3. 重新进入门禁一

### 暂停和恢复

**暂停：**
- 状态文件记录 `currentStage: "context"`
- 状态文件记录 `stageStatus.context: "blocked"`
- 状态文件记录 `stageStatus.planning: "pending"`
- 状态文件记录 `blockingItems: [{ code: "p0_unresolved", scope: "PRD-01", ... }]`

门禁一属于需求评审阶段：等待的对象是需求确认，责任在 context。上下文产物已生成不等于阶段完成——门禁没过就还没完成。把阻塞挂到 `planning` 会让恢复逻辑误判"已进入计划阶段"。

**恢复：**

开发下次调用：
```
继续 frontend-delivery。
需求标识：feature-001
```

AI 动作：
1. 读取状态文件
2. 检测到 `stageStatus.context: "blocked"`
3. 检查 `blockingItems`，发现 P0 问题未解决
4. 提示开发："仍有 1 个 P0 问题待确认：PRD-01。请提供产品回复。"

## 门禁二：计划批准

### 触发时机

plan.md 生成后，开始实现前。

### 通过条件

- **必须：** 所有 P1 问题已解决
- **必须：** 开发明确批准计划
- **允许：** P2 问题可以未解决

### AI 输出

```
技术计划已生成：
- docs/ai-delivery/<需求标识>/plan.md

计划摘要：
- 需要创建 {N} 个文件
- 需要修改 {N} 个文件
- 需要对接 {N} 个接口
- 可选估时：见 context.md（仅开发明确要求时展示）

P1 未解决问题：{count}个
{如果有 P1 未解决，列出问题和影响}

请确认是否批准计划？批准后我将开始修改代码。
```

### 开发回复处理

**情况 1：批准计划**

开发说：
```
批准计划，开始实现。
```

AI 动作：
1. 设置 `approvedPlanVersion` = 当前 `planVersion`
2. 设置 `approvedAt` = 当前时间戳
3. 设置 `approvedByRole` = "developer"
4. 追加到 decisions.md：
   ```markdown
   ## [DEV-001] 2026-08-13 15:00 开发确认
   
   **问题：** 批准技术计划
   
   **决策：** 批准 plan.md（版本 2026-08-13T14:30:00+08:00）
   
   **确认来源：** 开发批准
   
   **影响：** 开始修改代码
   
   **替代决策：** 无
   ```
5. 设置 `stageStatus.planning` = `"complete"`，`stageStatus.implementation` = `"active"`
6. 继续下一阶段

**情况 2：要求修改计划**

开发说：
```
不要创建新组件，用已有的 common-upload 组件。
```

AI 动作：
1. 根据反馈修改 plan.md
2. 更新 `planVersion`
3. 追加到 decisions.md：
   ```markdown
   ## [DEV-002] 2026-08-13 15:10 开发确认
   
   **问题：** 头像上传实现方式
   
   **决策：** 复用已有 common-upload 组件，不创建新组件
   
   **确认来源：** 开发反馈
   
   **影响：** 减少代码量，提高一致性
   
   **替代决策：** 原计划：创建 avatar-upload 组件
   ```
4. 重新请求批准

**情况 3：P1 问题未解决**

AI 输出：
```
计划已生成，但仍有 1 个 P1 问题未解决：

PRD-05: 列表加载失败是否支持重试？

此问题会影响错误处理流程。建议先解决后再批准计划。
```

开发补充：
```
PRD-05: 支持重试，最多 3 次。
```

AI 动作：
1. 更新 context.md 和 decisions.md
2. 更新 plan.md（如果需要）
3. 重新请求批准

### 暂停和恢复

**暂停（等待批准）：**
- 状态文件记录 `stageStatus.planning: "awaiting_confirmation"`
- 状态文件记录 `stageStatus.implementation: "pending"`
- 状态文件记录 `status: "awaiting_confirmation"`

等待批准仍属于 planning 阶段，不提前推进 implementation。

**恢复：**

开发下次调用：
```
继续 frontend-delivery。
需求标识：feature-001
```

AI 动作：
1. 读取状态文件
2. 检测到 `stageStatus.planning: "awaiting_confirmation"`
3. 提示开发："计划已生成，等待批准。请查看 plan.md 并确认是否批准。"

## 问题分级实战示例

### 示例 1：用户资料页面

| 问题 | 优先级 | 理由 |

| 问题 | 优先级 | 理由 |

## 常见误判纠正

### 误判 1：把 P1 当 P0

❌ **错误：** "列表分页参数格式？" 标为 P0

✅ **正确：** P1。虽然影响接口设计，但可以先按常见格式（page/pageSize）形成草案，产品确认后调整。

### 误判 2：把 P2 当 P1

❌ **错误：** "按钮文字？" 标为 P1

✅ **正确：** P2。文案细节不影响技术方案，可以给默认值"确认"，产品否决时改文案即可。

### 误判 3：把 P0 降级为 P1

❌ **错误：** "删除操作是否可撤销？" 标为 P1

✅ **正确：** P0。涉及数据安全，不可撤销的删除必须二次确认，错误实现可能导致数据丢失。

## 总结

**门禁设计原则：**
1. 最少门禁（只有 2 个）
2. 门禁位置关键（需求确认 + 计划批准）
3. 门禁条件清晰（P0 解决 / P1 解决 + 批准）

**问题分级原则：**
1. P0 = 不能错、不能猜
2. P1 = 影响方案、可以草案
3. P2 = 给默认值、记录理由

**判断技巧：**
- 问自己："如果这个问题错了，会导致什么后果？"
  - 数据错误/安全问题/业务错误 → P0
  - 返工/性能问题/测试不全 → P1
  - 改个文案/调个颜色 → P2
