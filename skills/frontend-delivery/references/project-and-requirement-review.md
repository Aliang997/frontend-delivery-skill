# 项目分析与需求评审

本文档定义 frontend-delivery skill 阶段一的四项工作：分析项目、分析需求、生成分级评审清单、分析复用与影响范围。

问题分级（P0/P1/P2）的判断标准和门禁规则见 `workflow-gates.md`，本文档不重复定义。

**能力说明：** 本文档描述的所有检查都使用当前 AI 客户端已有的能力完成，优先使用环境中更强的检索方式：

| 需要的能力 | 用途 |
| --- | --- |
| 代码与文本搜索（含语义或结构化检索，若可用优先） | 定位配置、依赖、同类实现、调用方 |
| 文件与目录读取 | 读配置文件、规范文档、需求文档、现有实现 |
| 项目命令执行 | 只用于读取信息（如查看已安装版本、列出脚本），不在阶段一改代码 |

缺少某项能力时，说明受影响的检查项，并请开发提供替代输入或手动执行。

## 第一部分：项目分析

### 核心原则：只分析与需求相关的部分

项目分析的目的是"能安全地写出这一个需求的计划"，不是"给整个仓库做体检"。机械扫描全部业务会产出大量无用信息，挤占上下文，还会让真正相关的风险被淹没。

**分两层执行：**

| 层级 | 范围 | 是否可省略 |
| --- | --- | --- |
| 全局层 | 技术栈、包管理器、构建与运行端、规范、可用命令、Git 状态 | 不可省略。任何需求都要知道"这是什么项目、怎么跑、怎么验" |
| 需求层 | 与本次需求直接相关的页面、组件、接口、工具、公共能力 | 按需求裁剪。与需求无关的业务模块不读 |

全局层是有界的（十几个配置文件级别的检查），需求层才是需要判断的部分。

### 如何界定"相关"

按下面顺序判断，命中任一条即为相关：

1. **需求文档直接点名的**：需求里提到的页面名、入口名、按钮、字段、接口、模块。
2. **入口链路上的**：从需求提到的入口到目标页面之间经过的路由、导航、守卫、布局。
3. **本次要复用或修改的**：与需求功能同类的已有实现（详见"第四部分：复用分析"）。
4. **本次要经过的公共能力**：请求封装、登录、权限、埋点、上传、弹窗、跨端 API，只要本次需求会调用就相关。
5. **会被本次修改影响的**：如果计划修改某个公共文件，它的调用方全部相关（这一步在复用分析里展开）。

**不相关的典型例子：**

- 与本次需求无关的其他业务模块的页面和接口
- 历史遗留但本次不会经过的功能
- 与本次需求无关的构建产物、文档、示例代码

**边界情况：** 无法判断某个模块是否相关时，先做一次低成本确认（读文件名和导出符号，不通读实现）。仍无法判断且它涉及登录、权限、支付、数据写入时，按相关处理并在 `context.md` 记为待确认。

### 全局层检查清单

| 检查项 | 线索来源 | 记录到 `context.md` | 无法确认时 |
| --- | --- | --- | --- |
| 项目规范 | 仓库根与文档目录下的规范文件、贡献指南、AI 指令文件、编辑器与格式化配置 | 开发规范 → 项目规范文档 | 多份规范并存且相互冲突时暂停询问优先级 |
| 依赖清单及版本 | 包描述文件的依赖字段；必要时读锁文件确认实际解析版本 | 技术栈各字段 | 声明版本与锁文件版本差异较大时以锁文件为准并记录差异 |
| 锁文件与实际包管理器 | 锁文件类型、包描述文件中声明的包管理器字段、工作区配置、CI 配置、项目规范里的安装说明 | 技术栈 → 包管理器 | 见下方"包管理器判断" |
| 构建工具与运行端 | 构建配置文件、脚本命令、产物目录配置 | 技术栈 → 构建工具 | 见下方"运行端判断" |
| 路由方案 | 路由依赖、路由配置目录、约定式路由目录结构、页面注册清单 | 技术栈 → 路由 | 无路由方案且需求要新增页面时，作为 P1 问题询问开发 |
| 状态管理 | 状态管理依赖、store 目录、全局注入点 | 技术栈 → 状态管理 | 存在多套状态方案时记录各自适用范围 |
| UI 组件库 | 组件库依赖、按需引入配置、主题覆盖文件 | 技术栈 → UI 组件库 | 存在多套组件库时确认本次应使用哪套 |
| 样式方案 | 预处理器依赖、原子化 CSS 配置、全局样式入口、设计变量文件、移动端适配方案 | 技术栈 → 样式方案 | 多套并存时记录各自使用场景 |
| 请求封装 | HTTP 库依赖、请求实例文件、拦截器、统一错误处理、基础地址配置 | 技术栈 → HTTP 库 | 无统一封装时记录并在计划中说明本次是否新增 |
| 登录能力 | 登录页、鉴权 token 存取、请求头注入、登录态刷新、单点或授权流程 | 项目能力 → 登录和权限 | 需求涉及登录但项目无登录能力时按 P0 处理 |
| 权限能力 | 路由守卫、权限指令或组件、按钮级权限判断、角色数据来源 | 项目能力 → 登录和权限 | 需求涉及权限但机制不明时按 P0 处理 |
| 埋点能力 | 埋点 SDK 依赖、埋点封装、事件常量表、上报时机 | 项目能力 → 埋点和统计 | 需求要求埋点但无现成能力时记为 P1 |
| 跨端能力 | 跨端框架依赖、条件编译标记、平台判断工具、平台专属 API 封装 | 项目能力 → 跨端能力 | 见下方"运行端判断" |
| Mock 能力 | Mock 依赖、mock 目录、开发服务器代理与拦截配置、环境开关 | 项目能力 → Mock 数据 | 无 Mock 能力时在计划中说明替代方案 |
| Lint / 类型检查 / 测试 / 构建命令 | 包描述文件的脚本字段（以脚本实际内容为准，不猜命令名）、CI 配置、项目规范 | 构建和验证命令 | 脚本存在但无法确认用途时读脚本内容；仍不确定时询问开发 |
| Git 分支与未提交修改 | 版本控制目录是否存在、当前分支、工作区改动列表 | Git 状态 | 见下方"未提交修改的归属" |

**记录要求：** 每一项都要写清"从哪个文件看出来的"。事实（文件里写着）、推断（从依赖组合推出）、假设（没有依据的猜测）必须分开标注，不能混成一句结论。

### 运行端判断

运行端决定验证方式、适配要求和可用 API，必须判断清楚。**下表是线索，不是唯一依据**：单条线索只提高置信度，最终结论要多条线索交叉验证。不同技术栈的配置文件名差别很大，不要把某个具体文件名当成必要条件。

| 运行端 | 依赖线索 | 配置线索 | 目录与代码线索 |
| --- | --- | --- | --- |
| Web 桌面站点 | 通用前端框架 + 通用构建工具，无移动端适配库 | 构建目标为浏览器，无移动端 viewport 特殊处理 | 页面按宽屏布局，存在断点较大的响应式样式 |
| H5 移动端 | 移动端组件库、移动端适配/rem/viewport 方案、手势或滚动库 | HTML 模板含移动端 viewport 与安全区设置 | 存在安全区、吸底、键盘弹起相关样式或工具 |
| PC 管理端 | 桌面端组件库、表格/表单/图表类依赖、权限相关依赖 | 存在较完整的路由与菜单配置、多级权限配置 | 存在布局壳（侧边栏 + 顶栏）、列表页与详情页大量复用同一套表格组件 |
| 小程序 | 小程序编译框架依赖、小程序专用 UI 库 | 存在小程序应用级与页面级配置、编译产物目标为小程序平台 | 页面按小程序生命周期组织，存在平台条件编译分支、平台专属 API 调用 |
| 多端同构 | 跨端框架依赖 | 构建脚本按平台参数分多个入口或多个产物目录 | 存在条件编译标记、平台判断工具、按平台分目录的实现 |

**判断步骤：**

1. 先看构建脚本有几个产物目标：一个目标通常是单端，多个目标是多端。
2. 再看依赖里有没有端专属库：小程序框架、移动端适配库、桌面端组件库。
3. 最后看代码里有没有平台分支：条件编译标记、运行时平台判断。
4. 三者一致时可以下结论；不一致时按最保守的结论（即需要验证的端最多）记录，并作为待确认项询问开发。

**必须询问开发的情形：** 构建脚本有多个端的产物目标，但需求没说明本次要覆盖哪些端。这直接决定适配工作量与验证范围，不能自己挑一个。

### 包管理器判断

按优先级取第一个能确定的：

1. 包描述文件中显式声明的包管理器字段（含版本）。
2. 仓库中唯一存在的锁文件类型。
3. CI 配置或项目规范文档中写明的安装命令。

**必须暂停询问开发的情形：**

- 存在多种锁文件（说明历史上换过包管理器，或有人用错工具装过依赖），无法确定哪个是当前生效的。
- 一个锁文件都没有，且包描述文件也没有声明。
- 声明的包管理器与锁文件类型不一致。

包管理器错了会导致依赖树与团队不一致、验证结果不可信，所以这一项不猜。**注意：** 阶段一只是"确认用哪个包管理器"，不代表可以执行安装；安装依赖需要单独授权。

### 未提交修改的归属

存在未提交修改时，必须区分：

| 归属 | 判断线索 | 处理 |
| --- | --- | --- |
| 开发本次需求的前置工作 | 改动文件与本次需求相关，且开发说明过 | 在计划中视为已有基础，避免重复实现 |
| 开发正在做的其他工作 | 改动文件与本次需求无关 | 标为不可修改范围，实现时绝对避开 |
| 无法判断 | 改动跨越相关与不相关文件，或没有任何说明 | **暂停询问开发** |

无法判断归属却直接动手，最常见的后果是覆盖掉开发未提交的工作，这类损失不可从版本控制恢复，所以必须问。

### 多项目分析

`projectPaths` 中每个项目**独立**完成上面全部检查，不假设它们技术栈相同（常见组合是 H5 + 管理端 + 小程序，三者栈可能完全不同）。

| 要求 | 说明 |
| --- | --- |
| 独立记录 | `context.md` 的项目画像按项目分节，每节有自己的技术栈、命令、能力 |
| 标注归属 | 所有文件路径、任务、接口、验证命令都标明所属项目 |
| 归属规则 | 文件属于"包含它且路径层级最深"的项目根目录，不按 `projectPaths` 声明顺序 |
| 公共代码 | 位于独立目录或独立仓库的公共代码，作为单独项目加入 `projectPaths` |
| 项目不可访问 | 记 `inaccessible_project` 阻塞项（scope 为该项目），不假设其实现，其他项目继续分析 |
| 需要暂停 | 文件不属于任何项目、项目根目录重叠后仍无法判断归属、存在循环依赖 |

### 项目分析中必须暂停询问开发的情形汇总

| 情形 | 为什么不能自己决定 |
| --- | --- |
| 无法确认实际包管理器 | 依赖树与团队不一致，后续所有验证结果不可信 |
| 无法确认目标运行环境 | 直接决定适配工作量、可用 API 与验证方式 |
| 多份项目规范冲突，无法确认优先级 | 代码风格与提交规范选错会导致整批改动被退回 |
| 无法确认未提交修改的归属 | 可能覆盖开发未提交的工作，损失不可恢复 |

暂停时遵守"一次只向开发提一个关键技术问题"：把最阻塞的一个问上去，其余写入 `context.md` 开放问题排队。

## 第二部分：需求分析的 12 个维度

对每个维度产出结论，并判断信息是否充分。信息不充分时不要留空，也不要自行补全，转化为评审清单里的问题。

| # | 维度 | 要产出什么 | 信息充分的判断标准 | 不充分时 |
| --- | --- | --- | --- | --- |
| 1 | 业务目标与成功标准 | 一句话业务目标 + 可度量的成功标准 | 能回答"上线后用什么现象判断这件事做成了" | 目标缺失记 P0；只是标准不可度量记 P1 |
| 2 | 目标用户、入口与前置条件 | 用户类型、每个入口的位置、进入前必须满足的条件 | 能画出"从哪来 → 到哪去"的完整路径，且每个入口都有归属 | 入口不明记 P1；入口涉及权限差异记 P0 |
| 3 | 页面、弹窗、抽屉与状态数量 | 可数的清单：N 个页面、M 个弹窗、每个的状态数 | 数字确定，没有"等等""若干"这类模糊表述 | 数量不确定记 P1，并列出你按什么假设计数 |
| 4 | 正常/加载/空数据/失败/重复操作流程 | 每个关键操作的五种流程分别怎么走 | 五种情况都有明确说法（含"不处理"也算明确） | 失败与重复操作缺失记 P1；涉及资金、写数据的重复提交记 P0 |
| 5 | 登录、注册、授权、权限与用户状态 | 未登录/已登录/无权限/受限用户分别看到什么 | 每种用户状态都有确定的界面与跳转结果 | 一律记 P0。权限边界猜错会造成数据暴露 |
| 6 | 前端、后端、产品、UI 职责 | 每项待办的负责方 | 每个待办都有唯一负责方，没有"两边都行" | 涉及校验、计算、状态流转的职责不明记 P0；其余记 P1 |
| 7 | 接口失败、重试与幂等归属 | 失败重试策略、幂等由哪一端保证、重复请求怎么处理 | 能回答"同一个请求发两次会发生什么" | 涉及写操作一律记 P0；纯读接口记 P1 |
| 8 | 跨端与平台差异 | 本次覆盖哪些端、各端行为差异、各端验证方式 | 端清单确定，差异点逐条列出 | 端清单不明记 P0（决定范围）；具体差异待定记 P1 |
| 9 | 敏感数据的传递、保存与上报 | 涉及哪些敏感字段、是否落地存储、是否进埋点、是否需要脱敏 | 每个敏感字段都有明确的传递/存储/上报结论 | 一律记 P0。合规问题不可事后补救 |
| 10 | 埋点与数据统计口径 | 事件清单、触发时机、参数、去重与归因口径 | 每个事件的"何时触发、带什么参数、怎么算一次"都明确 | 事件清单缺失记 P1；口径歧义记 P1，并写明你按哪种口径实现 |
| 11 | 明确不做的内容 | 本次范围外的功能清单 | 有显式的不做清单，不是靠"没提到"推断 | 主动提出你认为不做的项，请产品确认。**"没提到"不等于"不做"** |
| 12 | 可验证的验收标准 | 每条验收标准都能被一次具体操作检验 | 每条都能写成"做 X，看到 Y" | 标准不可验证记 P1，并给出你建议的可验证改写 |

### 维度分析的常见陷阱

**陷阱 1：把 UI 图当需求。** UI 图只描述"看到什么"，不描述"什么时候看到""失败了怎样"。维度 4、5、7 通常在 UI 图里找不到答案，必须单独确认。

**陷阱 2：把"没提到"当成"不需要"。** 需求文档没写加载态，不等于产品同意没有加载态。缺失项要主动列出并确认，不能沉默处理。

**陷阱 3：把技术方案写进需求理解。** "AI 对需求的理解"章节只写业务事实和规则，不写用什么组件、怎么拆文件。技术方案属于 `plan.md`。

**陷阱 4：把产品的愿望当成已确认结论。** 需求文档里的"最好能""后续考虑"不是本次范围，要放进"明确不做"或单独确认。

## 第三部分：生成评审清单

分级标准见 `workflow-gates.md`。本部分只讲"怎么把问题写成产品能直接回答的形式"。

### 问题的六个要素

`context.md` 的"产品待确认问题"表格每行必须完整填写六项：

| 要素 | 要求 | 反例 |
| --- | --- | --- |
| ID | `PRD-NN` 连续编号，一旦分配不复用、不重排（决策记录和阻塞项都靠它引用） | 改需求后重排编号，导致 `decisions.md` 的引用全部错位 |
| 优先级 | P0 / P1 / P2，按 `workflow-gates.md` 判断 | 全部标 P0（等于没分级，门禁失效） |
| 问题 | 一个问题只问一件事，用业务语言，不用技术术语 | "路由守卫是否需要校验 token？"（产品看不懂，且混了两个问题） |
| 确认原因 | 说明"不确认会导致什么" | "需要确认一下"（没有信息量，产品不知道为什么重要） |
| 影响范围 | 列出受影响的角色或环节：前端 / 后端 / UI / 测试 / 合规 | 留空（产品无法判断该拉谁一起决策） |
| 建议选项 | **互斥的 A/B（必要时 C）选项**，每项都是可直接选择的完整方案 | "您希望怎么处理？"（开放式提问，产品会回一段无法落地的描述） |
| 状态 | 待确认 / 已确认 / 已作废，产品回复后立即更新 | 一直停留在"待确认"，门禁无法判断是否可通过 |

### 建议选项必须互斥且可选择

开放式提问是评审清单最常见的失效原因：产品回一段自由描述，开发还要再来一轮才能落地。

**反例与改写：**

| 反例（开放式） | 改写（互斥选项） |
| --- | --- |
| 未登录用户的处理方式？ | A 跳转登录页，登录后回到原页面 / B 展示只读内容，操作时才要求登录 / C 直接展示无权限提示 |
| 列表加载失败怎么办？ | A 整页错误提示 + 重试按钮 / B 保留已加载数据 + 顶部提示条 / C 静默失败，只记录日志 |
| 昵称有什么限制？ | A 最长 20 字符，允许中英文数字 / B 最长 40 字符，允许中英文数字 / C 不限制长度，仅过滤空白字符 |
| 需要支持批量操作吗？ | A 本次支持批量，含全选与批量删除 / B 本次不支持，后续需求再做 |

**写选项的三条规则：**

1. **每个选项都是可直接实现的完整方案**，不是方向描述。"做好一点"不是选项。
2. **选项之间互斥**，产品只能选一个。出现"A 和 B 都要"说明这是两个问题，拆开。
3. **P2 问题给默认方案而不是选项**，格式为"默认：<方案>（理由：<依据>）"，让产品只需要在否决时回复。

### 提问规则

| 对象 | 规则 |
| --- | --- |
| 产品 | 集中生成**可直接转发**的完整清单，一次给全，避免反复转发。清单本身不含技术术语、不含项目内部路径 |
| 开发 | **一次只提一个关键技术问题**。其余技术问题写入 `context.md` 开放问题排队，等这个问完再问下一个 |
| 所有人 | 能从项目代码里确定的信息不问。问之前先搜一遍代码 |

**可转发清单的写法：** 从 `context.md` 表格里摘出 ID、优先级、问题、确认原因、影响范围、建议选项六列，去掉项目内部路径和技术细节，形成独立段落。产品不需要打开 `context.md` 就能回答。

**回复处理：** 产品回复后立即做三件事——更新表格状态列、追加 `decisions.md`（不覆盖历史）、重新计算需求评审结论区块。产品结论与原需求冲突时按需求变更处理，见 `change-control.md`。

### 需求评审结论区块

`context.md` 末尾必须有这个区块，它是门禁一的判定依据：

```markdown
## 需求评审结论

- 评审状态：待确认 | 已确认
- P0 未解决：<数量>
- P1 未解决：<数量>
- 是否允许进入最终技术计划：是 | 否
```

**填写规则：**

| 字段 | 规则 |
| --- | --- |
| 评审状态 | P0 全部解决且开发确认需求理解 → 已确认；否则待确认 |
| P0 未解决 | 表格中优先级为 P0 且状态为"待确认"的行数。必须与表格实际一致 |
| P1 未解决 | 同上，统计 P1 |
| 是否允许进入最终技术计划 | P0 未解决 > 0 → 否；P0 = 0 且 P1 > 0 → 是，但只能出标注假设的**计划草案** |

P0 未解决时同步记 `p0_unresolved` 阻塞项，scope 为具体问题 ID（如 `PRD-01`），一个未解决 P0 一条。

## 第四部分：复用分析

### 四分类

| 分类 | 定义 | 判断标准 | 记录要求 |
| --- | --- | --- | --- |
| 直接复用 | 现有实现能满足需求，一行不改 | 输入输出、交互、状态、样式都与需求一致；只是被新代码调用 | 路径 + 用途 + 用在本次哪个位置 |
| 修改后复用 | 现有实现方向正确，需要扩展或调整 | 需要加参数、加状态、加分支，但主体逻辑保留 | 路径 + 改什么 + **谁在用**（调用方清单）+ 是否向后兼容 |
| 必须新增 | 现有代码没有可用基础 | 搜索后确认无同类实现，或改造成本高于新写且会污染现有能力 | 建议路径 + 为什么不能复用（写清搜过什么） |
| 与需求无关 | 与本次需求无关的实现 | 不在需求链路上，也不会被本次修改影响 | 只在容易被误认为相关时列出，说明为什么排除 |

**"修改后复用"和"必须新增"的边界：** 判断依据是"改造会不会影响现有调用方"。改造只加可选参数、默认行为不变 → 修改后复用。改造会改变现有调用方的行为 → 要么新增，要么先询问开发。

### 如何搜索候选

按类别分别搜索，不要只搜一遍就下结论。每类都用"功能词 + 同义词 + 目录约定"三种方式交叉搜索。

| 类别 | 搜什么 | 搜索线索 |
| --- | --- | --- |
| 页面 | 同类页面（同样的列表/详情/表单/结算形态） | 路由配置里的路径与名称、页面目录名、页面标题文案 |
| 组件 | 同类交互组件 | 组件目录、组件注册处、需求中的交互名词（上传、选择器、步骤条） |
| 接口 | 同域接口封装 | 接口目录按业务分的模块、请求方法命名、接口路径中的业务词 |
| 工具 | 格式化、校验、存储、日期、金额、防抖节流 | 工具目录、通用函数命名 |
| 登录 | 登录流程、登录态存取、登录后回跳 | 鉴权相关命名、请求拦截器、路由守卫 |
| 权限 | 路由级与元素级权限判断 | 守卫、权限指令或高阶组件、角色与权限码数据结构 |
| 埋点 | 埋点封装、事件常量 | 埋点 SDK 初始化处、事件常量表、既有埋点调用点 |
| 跨端 | 平台判断、条件编译、平台 API 封装 | 条件编译标记、平台工具函数、平台专属目录 |
| 测试能力 | 同类功能的现有测试 | 测试目录、测试文件命名约定、测试配置中的匹配规则 |

**搜索深度控制：** 每类找到 1-3 个最相关的候选就够，不需要穷举。找到候选后读它的实现和一处调用点，确认它真的能用——只看文件名就判定可复用是常见错误。

### 影响范围分析

对每个"修改后复用"的目标，必须回答：

1. **谁在用？** 搜出全部调用方，列出清单。调用方超过 5 处的，标为高影响。
2. **改动向后兼容吗？** 现有调用方不改代码还能正常工作吗？
3. **有没有隐式依赖？** 有没有代码依赖它当前的具体行为（返回值形状、副作用、时序）？

调用方清单要写进 `context.md`，它是门禁二判断计划风险的依据，也是验证阶段回归范围的来源。

### 必须询问开发的情形

| 情形 | 为什么不能自己决定 | 怎么问 |
| --- | --- | --- |
| 存在多套相似实现，无法确定哪套是主实现 | 选错会在废弃分支上开发，代码合并时被删掉 | 列出各套的路径、最近改动时间、调用方数量，问哪套是当前主实现 |
| 修改公共能力可能影响旧业务 | 影响范围超出本次需求，回归成本由开发承担 | 列出调用方清单和改动内容，问是"改公共能力"还是"本次单独实现" |
| 提取公共组件会显著改变范围 | 重构属于额外工作量，需要开发决定是否本次做 | 给出"本次不提取（快，有重复代码）"和"本次提取（慢，影响 N 处）"两个选项 |

这三种情形都符合"影响范围不确定"，属于必须暂停的类别。暂停时把未确认事实、影响和建议选项写入 `context.md` 开放问题。

## 常见误判纠正

### 误判 1：把项目分析做成全仓库扫描

不对：逐个读完所有业务模块，产出一份完整的项目文档。

正确：全局层查配置和命令，需求层只查相关实现。判断标准是"这个信息会改变本次的计划吗"，不会就不查。

### 误判 2：靠单个配置文件名判断技术栈

不对：看到某个特定文件名就断定框架和运行端。

正确：依赖 + 构建配置 + 目录结构三方交叉验证。不同团队的目录约定差别很大，同一个框架也有多种脚手架布局。

### 误判 3：把可以查到的信息拿去问开发

不对：问"项目用什么状态管理""构建命令是什么"。

正确：这些从依赖清单和脚本字段就能确定。问之前先搜。核心原则是"能从项目确定的不问开发"。

### 误判 4：把待确认问题写成开放式提问

不对：`PRD-03 | P1 | 表单校验规则是什么？ | 需要确认 | 前端 | 请产品说明 | 待确认`

正确：`PRD-03 | P1 | 手机号校验失败时如何提示？ | 决定错误提示位置与阻断时机 | 前端、UI、测试 | A 输入框下方红字提示，不阻断继续输入 / B 失焦时弹出提示，阻断提交 | 待确认`

### 误判 5：把所有问题都标 P0

不对：为了"稳妥"把 12 个问题全标 P0。

正确：全是 P0 等于没有分级，门禁一永远过不去，评审失去意义。按 `workflow-gates.md` 的标准判断，问自己"这个问题答错会造成数据/安全/业务错误吗"。

### 误判 6：只看文件名就判定可复用

不对：搜到一个名字匹配的组件，直接写进"直接复用"。

正确：读它的实现和一处调用点，确认参数、状态、交互都满足需求。名字像但行为不符的组件，改造成本可能高于新写。

### 误判 7：把需求文档没提的内容当成"不做"

不对：需求没写空数据状态，就按没有空数据处理。

正确：主动列入待确认清单。"明确不做"必须来自产品的显式确认，不能来自沉默。

### 误判 8：在阶段一就设计技术方案

不对：在"AI 对需求的理解"里写要创建哪些文件、用什么组件。

正确：阶段一只产出需求事实、项目事实和待确认问题。文件清单和技术任务属于 `plan.md`，门禁一通过后才写。

## 总结

**项目分析：**
1. 全局层必查（栈、命令、规范、Git），需求层按相关性裁剪
2. 运行端和包管理器多线索交叉验证，不靠单个文件名
3. 四种情形必须暂停：包管理器、目标环境、规范优先级、未提交修改归属
4. 多项目独立分析，所有产出标注项目归属

**需求分析：**
1. 12 个维度逐项产出结论，不留空、不自行补全
2. 涉及权限、敏感数据、写操作幂等的不确定项一律 P0
3. "没提到"不等于"不做"

**评审清单：**
1. 六要素齐全，缺一项产品就答不了
2. 建议选项必须互斥、可直接选择，禁止开放式提问
3. 产品清单集中给，开发问题一次只问一个
4. 评审结论区块的数字必须与表格实际一致

**复用分析：**
1. 四分类：直接复用 / 修改后复用 / 必须新增 / 与需求无关
2. 九个类别分别搜索，找到候选要读实现验证，不看名字下结论
3. "修改后复用"必须附调用方清单和兼容性判断
4. 主实现不明、影响旧业务、范围显著变化 → 询问开发

**判断技巧：**
- 问自己"这个信息会改变本次计划吗？"→ 不会就不查
- 问自己"这个问题能从代码里查到吗？"→ 能就不问
- 问自己"产品看到这个问题能直接回一个字母吗？"→ 不能就重写
- 问自己"改这个文件会影响本次需求之外的功能吗？"→ 会就暂停询问
