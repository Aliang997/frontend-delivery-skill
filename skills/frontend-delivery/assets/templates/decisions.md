## 写入规则

1. 只有**已确认**的结论进本文件。未确认内容留在 `context.md` 的开放问题，不写入这里。AI 给出的默认方案属于推断，开发或产品明确接受后才能追加记录——沉默和未否决都不算接受。
2. 每次人工确认后立即追加，不批量补记。
3. 决定被推翻时**新增**一条记录，并在新记录的"替代决策"中引用被推翻的记录 ID；不修改旧记录正文。
4. 确认人未提供姓名时**只记录角色**（产品、开发、UI、后端），不得虚构姓名。
5. 编号在各自类型内递增，不复用：`DEC-*` 产品确认、`DEV-*` 开发确认、`CR-*` 需求变更、`UCR-*` UI 变更、`TECH-*` 技术调整。
6. 缺陷修复不抬为需求变更，不在本文件建 `CR-*`；按缺陷处理并记录在 `delivery.md`。
7. 本文件禁止记录账号、密码、Token、验证码及其他凭证。

## 字段规范

本节是填写说明，不是记录内容，生成实际文件时保留本节即可（也可删除）。

**所有类型的公共字段：**

| 字段 | 说明 |
| --- | --- |
| 标题 | `## [<ID>] <YYYY-MM-DD HH:mm> <类型>` |
| 关联问题 | `context.md` 中的问题 ID，或"计划批准""实现冲突项""无" |
| 问题 | 需要决策的事项 |
| 决策 | 确认后的结论 |
| 确认来源 | 角色 + 途径，如"产品回复，由开发转述" |
| 影响 | 受影响的文件、任务、状态字段或门禁 |
| 替代决策 | "无"，或"替代 `<旧ID>`（原决策：<内容>）" |

**`CR-*` 与 `UCR-*` 额外字段：**

| 字段 | 说明 |
| --- | --- |
| 原内容 | 变更前的需求或 UI 描述 |
| 新内容 | 变更后的描述 |
| 变更来源 | 谁提出、经谁确认 |
| 影响项目 | 涉及的项目名，多项目时逐个列出 |
| 受影响 | 需要重做的页面、接口、代码、测试 |
| 不受影响 | 明确不动的部分，避免过度返工 |
| 处理结论 | 是否重批计划、何时实现 |
| 需求版本 | `CR-*` 专有，变更后的 `requirementVersion` |

变更分类标准、影响分析维度和分阶段处理规则见 `references/change-control.md`。
