# 恢复与流程切换

先找到当前事实和授权，再决定续做位置；状态规则统一见 state-machine.md。

## 恢复入口

1. 查看当前对话的目标、授权、操作限制与最后结果。
2. 若有 task.md，核对范围、任务、问题和证据；若有完整产物，再读与当前待办相关的正文；只有实际存在 workflow-state.json 时才读取并按状态机核对。
3. 使用下述恢复基准对照实际文件、需求、UI 和接口来源，检查中断期间是否变化。JSON 的 complete 不能代替事实。
4. 按受影响任务核对批准、依赖、阻塞和失效，确定仍有效的结果。
5. 简述接续范围及待确认项，在现有授权内继续；没有状态文件不代表必须重启完整流程。

定位产物只搜索当前项目相关目录；同名多份且无法确认归属时询问，不能仅凭修改时间选择“最新版”。
输入缺失、无法读取或状态损坏时保留已有文件，先利用可确认信息，不能从模板重置覆盖。
模式与终点以用户最新明确请求为准；“按方案开始实现”可扩展终点，单纯批准计划不自动扩展。
旧状态保留原 executionMode 和 targetStage，不因验证受限或实现交接分工改写。接续已经完成代码交接且验证由用户负责的记录时不重复实现；用户提供验证结果或明确要求继续跟进时，再恢复对应验收工作并更新状态。

## 轻量恢复基准

需要跨会话、交接或等待外部回复并稍后续做时，在当前记录保留基准：常规流程放 task.md；完整流程的代码、输入和配置文件基准放 context.md，Figma 设计基线及页面映射放 plan.md。不同文件不重复记录同一基准，也不为恢复另建快照文件或 JSON 字段。
默认记录采集时间、相关资料来源或版本、本次依赖文件的项目相对路径及待办引用。Git 项目同时记录 HEAD、相关范围的 `git status --short` 和 `git diff`；相关内容已暂存时补 `git diff --cached`。只检查当前任务涉及的项目和文件，不扫描全仓；这些只读命令仍须遵守项目与用户限制。
恢复时在相同范围重新取得 Git 状态与差异并和已有基准比较，查看相关文件是否新增、删除、重命名或内容变化。Git 结果描述的是工作区相对 HEAD 的当前差异；旧基准缺失时不能据此声称中断期间没有变化，应重读当前待办依赖的文件。
非 Git 项目或 Git 外部输入优先记录来源版本、修改时间和大小。只有确实需要判断字节是否完全一致时，才由系统工具计算并记录内容哈希；不得由模型自行推算，也不因等待外部回复默认采集。
任何基准变化只触发相关范围核对，不自动判定需求变更；纯换行差异按 SKILL.md 处理。文件一致也不能证明外部契约、环境或批准仍有效，仍需核对对应来源和前提。
Figma 是远程来源，不能用本地 Git 结果判断是否变化。计划已记录节点基线且命中 ui-restoration.md 的变更检测条件时，恢复前重新读取本次使用的节点；来源变化按 change-control.md 处理，访问失败只保留未核对范围，不重置全部任务。
旧记录没有基准时，局部重读当前待办所需资料并补齐，不回退到全仓扫描。完成本轮核对与处理后，再在需要挂起或交接时更新基准，不能恢复前先覆盖旧值。

## 升降级

执行中发现原判断未覆盖的跨项目、共享内容、公共组件行为、公共配置、跨模块联动或实际依赖时，立即按 SKILL.md 的顺序重新判断，不能沿用原流程深度完成交付。
由小改动升级为常规：命中上述常规流程下限、出现多个待确认点或需跨会话记录时，提取已有事实与授权，不重复已完成分析。
由常规升级完整：高风险关键规则仍不明确、涉及不可逆外部操作或数据迁移、复杂依赖、跨项目契约、数据协议、版本共存或实质兼容风险，或需要可追溯的多任务独立批准、局部失效及跨会话恢复时，再按实际需要逐步生成产物。权限、资金、隐私或敏感数据等主题规则明确且影响局部时保留常规流程并执行对应风险检查；仅跨越项目或模块且影响可控，或只复用公共组件，也不自动升级完整流程。
迁移已有验收项、任务 ID、真实确认、未决问题与验证证据；缺少批准范围或版本依据时只确认缺口，不能把“做过”当作“批准过”。
迁移完成后原 task.md 只保留转向新产物的说明，不同时维护两份活动任务和状态。
完整流程降为常规只在范围已缩小且复杂性与风险已消除时进行。task.md 接收必要事实、授权、未决项和证据；旧产物标明归档与去向，保留历史。
不能用降级清掉阻塞或绕过必要验证；仅剩一个文件也可能仍是高风险。
只改执行终点不一定改流程深度，反之亦然。

## 旧状态迁移

缺 schemaVersion 或旧全局批准字段的状态先按旧格式读取，再核对对应正文和实际记录。
保留旧记录；迁移版本 2 时在 decisions.md 写明来源格式、原批准范围与版本、迁移依据和未能确认的内容。
旧全局批准只有在能证明原批准覆盖的计划、任务和当前内容一致时，才映射为 taskApprovals。
没有任务版本的旧任务可按当前已核对定义初始化为 1，但不能因此推断当前内容获批；不明确的任务先保持未批准。
保留未解决阻塞和失效范围；未知 code 不丢弃原因，可在明确语义后映射 pending_decision 并记录原值。
版本 2 保存前补全必需字段和真实时间，确认正文与索引一致后再替换旧状态，不能静默丢失历史。
未知更高 schemaVersion、无法理解的字段或相互矛盾记录，保留原文件并说明需澄清部分，不猜语义重写。

## 典型恢复情形

- 需求缺失：使用足够明确的用户文字；确实无法确定目标时索取最少输入。已有范围可继续分析。
- P0/P1 未决：按问题定位相关任务及下游，保留独立工作；review_only 仍可交付评审与缺口。
- 计划未批准：展示已有草案和待批准任务版本，不重新生成；planning_only 可交付草案并结束。
- 接口冲突或缺契约：补齐可信来源后更新受影响计划；真实对接不以 Mock 通过代替。
- UI 缺失：先检查文字及项目认可模式是否足够，只有关键设计未知才等待补充。
- 项目不可访问：恢复路径或权限后只补该项目与依赖它的分析，不猜另一项目实现。
- 工作区重叠：保留双方改动，澄清冲突范围和处理方式；完整流程建立 pending_decision 索引。
- 验证失败：先区分本次、既有或未知，按 testing-and-delivery.md 修复或处理风险。
- 必要验证被禁止或环境不足：记录未执行及执行者；本次包含验收时等待用户结果，仅委托实现交接时按既定终点结束，不能改写成通过。
- 变更后恢复：计划内容更新后解除对应 planning 失效，批准另行核对；实现和验证保留到实际重做完成。
- 多个阻塞同范围：解除一项不能顺带移除其余原因。
- 目录迁移或跨系统恢复：先重新定位项目与产物，核对路径段、大小写和当前权限，不照搬本机命令。

这些情形用于按需核对，不要求每次运行全部场景。完成目标后停止，不为维持流程继续生成额外产物。
