# Frontend Delivery

版本升级记录见 CHANGELOG.md。

按影响和不确定性选择流程深度，按用户意图确定执行终点。先处理真实需求，再决定需要哪些记录。

## 入口判断

1. 读取本次用户要求及目标文件适用的项目规范，确认授权、禁止操作和已有工作。
2. 判断用户要的是评审、计划还是实际修改；只问解释、对比或审查 skill 本身时，不启动业务交付流程。
3. 先从当前对话和指定记录判断是否继续同一需求。已有记录按 references/recovery-scenarios.md 恢复，不因缺少 JSON 就重开任务。
4. 根据相关代码和需求按“完整流程硬条件、常规流程下限、小改动全部条件”的顺序判断流程深度，再独立判断本次命中的风险场景；不能仅按代码行数或风险关键词分类，无法确定流程深度时使用常规流程。
5. 多步骤任务用一句话说明范围、流程深度和验证方式。小改动不输出仪式化计划。

## 流程深度与风险检查

流程深度决定协作、记录和批准强度；风险检查决定本次必须核对的行为边界和验证项。两者分别判断：命中风险场景不自动进入完整流程，进入小改动也不能跳过与改动直接相关的检查。

完整流程：
- 命中以下任一情况时使用：权限、资金、隐私或不可逆后果的关键规则仍不明确；涉及不可逆外部操作或数据迁移；涉及跨项目契约、数据协议、版本共存、实质兼容风险或复杂依赖；需要可追溯的多任务独立批准、局部失效或跨会话恢复；正式验收、发布准备或跨团队交接无法用简短记录可靠推进。
- 仅跨越文件、项目或模块且影响可控，或只复用公共组件，不自动进入完整流程。
- 按理解需求、制定计划、实现、验证、交付推进；允许已确认且获准的独立任务先执行。
- 按实际追踪需要逐步创建产物，职责见“产物与信息归属”；不预先复制空文件。
- 两类关键确认分别是业务规则确认和受影响实现方案批准；已有有效确认不重复索取。启用完整状态记录时，字段只以 references/state-machine.md 为准。

常规需求：
- 同时修改多个项目，或修改被多个项目或模块共享的内容、公共组件行为、公共配置，或产生跨模块联动时，最低使用常规流程。
- 权限、资金、隐私或敏感数据、写操作幂等、不可逆后果等主题与本次改动相关，但规则明确、影响局部且没有复杂依赖时，最低使用常规流程，并执行对应风险检查。
- 需要梳理接口、交互、状态、目标端或专项验证，且影响可隔离、依赖与兼容边界明确时使用常规流程。
- 用简短清单记录范围、任务、必要问题和验证方式；只在真实决策点询问。
- 当前对话可完成时不落盘。跨会话、需要交接、有多项待确认内容、需要等待外部回复并稍后续做或用户要求记录时，使用 assets/templates/task.md。
- 用户已授权且无未决关键问题的任务直接执行，不要求另说“批准计划”。

小改动：
- 仅在未命中完整流程或常规流程下限，且同时满足以下条件时使用：只修改单个项目；影响限于局部页面或模块；预期行为明确；不改变共享内容、公共组件行为、公共配置或跨模块联动；不涉及需要单独核对的权限、资金、隐私或敏感数据、写操作幂等、不可逆后果或实质兼容风险；没有未决关键问题。
- 读相关规范和代码，完成已授权修改，检查差异，简短说明结果与验证情况。
- 不强制需求标识、UI 目录、全局画像、计划审批或产物文件。
- 本入口足够指导时，不加载其他参考文件。

先根据本文件“按需读取”列出的风险场景判断本次改动相关性。项目存在某项能力或需求出现某个关键词，本身不触发检查；该能力可能受到本次改动影响时才读取 references/frontend-risk-checks.md 的对应章节，一个任务可命中零项、一项或多项。权限、写操作幂等和敏感数据仍执行最低相关性判断，相关时不得跳过。

执行中发现新的跨项目范围、共享能力、公共配置、依赖、契约或风险时，立即重新判断流程深度与风险场景；小改动命中常规下限时至少升级为常规流程，命中完整流程硬条件时再升级完整流程。升级只补缺失步骤，保留已有任务、决策和有效授权；降级不得绕过未解决风险。切换与恢复见 references/recovery-scenarios.md。

最小分流示例：
- 单项目单页面修改明确按钮文案，没有公共影响或专项风险：小改动。
- 两个项目分别修改互不依赖的局部配置：常规需求；配置构成两端约定时升级完整流程。
- 修改公共按钮组件行为并核对调用方：常规需求。
- 修改跨项目登录协议或权限模型：完整流程，并检查对应权限、契约和兼容风险。
- 开始时判断为小改动，实现中发现必须修改公共配置：立即升级常规需求，只补新增范围需要的步骤。

## 对话输出

- 小改动默认一至三项，只说改动、实际检查和未解决问题；仅在失败、存在风险或用户要求细节时展开。
- 常规需求默认三至六项，覆盖范围、主要动作、相关风险、验证结果和必要下一步；简单结论不要展开成完整检查表。
- 完整流程在对话中优先报告结论、需用户决定的问题、阻塞、关键风险和产物位置；详细任务、状态和证据留在对应产物。
- 所有流程都不默认列出未触发的风险、无问题文件、重复状态迁移或与当前决策无关的过程。用户要求完整评审、明细或审计记录时再展开。

## 执行终点

保留以下模式，用户不必填写枚举值：
- review_only：只做评审。评审工作完成与需求已经确认分别报告。
- planning_only：只产出计划或标明缺口的草案。计划编写完成与计划获准实施分别报告。
- full_delivery：完成用户要求的实现与验证交接，不代表必须使用完整流程，也不包含自动发布。

用户明确只委托实现和交接、验证由其负责时，完成代码与交接清单后可以结束本次工作，并明确整体验收待验证；完整流程仍保留原 targetStage 和未完成的验证、交付状态，等待用户提供结果或明确调整总体范围。仅因命令被禁止或环境不足，不能自行缩小终点；已有明确委托分工不重复确认。

未显式给模式时，按自然语言确定。“先看看需求”不等于让 AI 改代码；“开始实现”是明确执行意图，不要求专用升级口令。
“继续”默认沿用原终点。新请求可以扩大或缩小终点，但不代替尚未解决的业务决策。
有阻塞时可以完成评审或草案交付；不得把草案说成可直接实施的最终方案。

## 所有流程共有的约束

- 先找资料和代码依据。事实、推断、待确认问题分别记录，已有明确规范不重复询问。
- 每次先判断本次行为及影响范围是否涉及权限、写操作幂等和敏感数据；涉及的必须核对已有规则及实现边界，无法判断则查明，明确无关即可略过。不为无关小改动展开全项目检查或额外生成记录。
- 只实现已确认行为和本次必要改动；低风险默认处理不能顺带增加功能。
- 不编造接口 URL、字段、错误码或关键 UI 设计。既有组件和明确文字规格可以作为依据。
- 只改需求相关代码，保留无关改动，清理本次造成的无用内容。
- 不因工作区存在其他改动就全部暂停；真实冲突只阻塞受影响范围。
- 验证只在用户和项目允许时执行。禁止测试或构建时，记录未执行及人工步骤，不以“只读检查”绕过限制。
- 依赖安装、配置、Git 写入、部署和外部操作遵守已有授权及项目规则；用户要求自行操作的，只提供清单。
- 凭证和真实个人数据不写入产物；不自行上传项目资料到外部服务。
- 只基于真实证据报告通过。代码已修改、验证完成、发布就绪是不同结论。

## 按需读取

- 需求不清楚、需要确认项目能力、复用边界或影响范围：references/project-and-requirement-review.md
- 存在真实决策、关键缺口、范围授权或任务批准问题：references/workflow-gates.md
- 需要制定 UI、数据流、文件或验证方案：references/planning-and-ui.md
- 按图片、截图或 Figma 节点还原 UI，或还原明确动效：references/ui-restoration.md
- 涉及接口、Mock、共享状态、数据转换、契约冲突，或完整流程任务执行前提：references/implementation-and-api.md
- 需要正式验证证据、人工交接、代码评审、CI、发布准备或处理验证失败：references/testing-and-delivery.md
- 先判断异步查询、缓存、金额日期、权限写操作、表单弹窗、性能多端、发布兼容，以及国际化、主题、浏览器、SSR/Hydration、SEO 是否与本次改动相关；只读取 references/frontend-risk-checks.md 中实际命中的章节。
- 需求、UI、接口、授权范围或已批准方案发生可能影响基线的变化：references/change-control.md
- 跨会话接续、等待后恢复、流程切换或旧记录迁移：references/recovery-scenarios.md
- 完整流程需要正式任务版本、任务级批准、阻塞与失效索引、跨会话状态或迁移时：references/state-machine.md

启用完整状态记录后，遇到表中未明确列出的状态或执行资格问题，查 references/state-machine.md 的对应章节；其他问题按上述职责查相关文件，不能默认加载全部。
不要为了确认某文件“不适用”而加载它。每次只读当前动作需要的规则；已读取、仍在上下文且未变化的内容直接复用，其他文件不重复定义其内容。

## 产物与信息归属

单项目默认目录：项目根目录/docs/ai-delivery/需求标识/
多项目默认目录：工作区根目录/docs/ai-delivery/需求标识/
用户指定位置优先。需落盘但没有标识时，可按日期与需求短名生成无冲突标识并告知；多个已有候选需求时先定位，不猜归属。

常规需求的 task.md 是当前记录；完整流程按实际内容选择以下产物：
- context.md：需求来源多、涉及多个项目、存在开放问题或需要交接上下文时，记录事实来源、需求与验收项、复用影响和开放问题。
- plan.md：存在多个任务、依赖、实施顺序或需要正式方案时，记录任务、版本、依赖、实现依据及验证方案。
- decisions.md：存在需要追溯的业务决定、方案取舍、批准或范围变化时追加记录，不记普通进度。
- delivery.md：需要正式验收、验证证据、发布准备或跨人交接时，记录任务结果、证据、未验证项、风险和人工步骤。
- 项目已有的代码评审、CI 和发布要求按 references/testing-and-delivery.md 衔接，记录在当前交付结果中，不另建流程。
- workflow-state.json：需要任务级批准、多个阻塞或失效范围、跨会话恢复或旧状态迁移时，记录阶段摘要、批准与阻塞索引，不复制正文。

按需使用 assets/templates/ 中同名模板。只保留本次实际需要的章节；不适用内容整节删除，禁止保留空标题、模板提示或占位符。必要信息无法确认时标记待确认并说明影响，不得为了填满模板而编造内容。
同一信息只维护一处，其他位置引用稳定 ID。只更新变化段落，估时引用现有任务 ID，不另建任务清单。

## 跨平台文本与路径

- 本 skill 的文本源文件使用 UTF-8 无 BOM、LF 换行。
- 读取已有文本兼容 LF、CRLF；内容比较先统一换行，不把换行差异当作需求或方案变化。
- 修改业务文件及生成项目产物时，遵循用户和项目的 .editorconfig、.gitattributes 等有效约定。
- 项目未规定时，新文本用 UTF-8 无 BOM、LF；已有文件保留编码和换行，不顺手整文件转换。
- 命令与路径适配 Windows、macOS、Linux，使用当前系统支持的能力，不写死 PowerShell、Bash、盘符或反斜杠。
- 相对输入路径以已确认工作区为基准；实际操作使用规范化路径，正确处理中文、空格和系统大小写规则。
- JSON 路径须合法转义；文档中的正斜杠示例不是强制宿主系统路径格式。
- 换电脑或操作系统后重新定位项目及产物，不将旧机器绝对路径直接用于写入。

## 范围

支持 Web、H5、PC 管理端和小程序。不承担原生 iOS、Android 开发；其他跨端项目先确认运行与验证条件。
本目录流程图用于理解同版本流程结构；具体执行以本入口和参考文件为准，流程图不参与加载和执行判定。
