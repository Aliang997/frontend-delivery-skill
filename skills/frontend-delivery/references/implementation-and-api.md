## 第一部分：实现顺序

### 六步顺序

按 `plan.md`"技术任务及依赖"的顺序执行，**跳过不适用的步骤**。下面六步是通用框架，不是每个需求都要走完。

| # | 步骤 | 适用范围 | 跳过条件 |
| --- | --- | --- | --- |
| 1 | 优先复用现有页面、组件、接口和工具 | 全部需求 | 不跳过。任何需求都先看有没有现成的 |
| 2 | 页面类需求建立必要的路由、页面骨架、样式、响应式和交互 | 页面新增、页面改版 | 非页面类需求跳过 |
| 3 | 逻辑、接口、埋点、Bug 修复类需求直接执行对应技术任务 | 逻辑/接口/埋点/Bug 类 | 页面类需求走第 2 步 |
| 4 | 仅在契约明确时对接真实接口 | 涉及接口的需求 | 契约缺失时只做已批准的 Mock 或独立逻辑 |
| 5 | 处理已确认的加载、失败、防重复、权限和平台差异 | 涉及以上任一的需求 | 各子项按"是否已确认"分别判断 |
| 6 | 按计划补充测试，并删除本次修改产生的无效代码和资源 | 全部需求 | 不跳过。清理是本次工作的一部分 |

**第 3 步的关键点：** 逻辑类、接口类、埋点类、Bug 修复类需求**不强制创建页面结构**。为一个纯逻辑修改新建页面文件或组件文件是典型的过度实现。

**第 5 步的关键点：** 只实现"已确认"的部分。加载态没确认就不自己设计加载态，权限规则没确认就不自己定权限判断。未确认的部分属于阻塞项，不是自由发挥空间。

**第 6 步的清理边界：**

| 可以删 | 不可以删 |
| --- | --- |
| 本次新建后又废弃的文件 | 本次之前就存在的未使用代码 |
| 本次修改导致不再被引用的导入、变量、函数 | 本次之前就存在的死代码 |
| 本次引入后未使用的资源文件 | 与本次改动无关的注释、日志 |
| 本次调试用的临时代码与临时文件 | 别人的调试代码 |

发现本次之前就存在的死代码时，在 `delivery.md` 的遗留事项里提一句，**不删**。

### 不预设框架写法

进入实现前，必须先读项目现有的同类文件，对齐五个方面。**不要凭对某个框架的一般认知直接写代码。**

**要读哪些文件（对齐检查清单）：**

| # | 读什么 | 对齐什么 | 判断标准 |
| --- | --- | --- | --- |
| 1 | 与本次要创建的文件最同类的 2-3 个现有文件（同为页面 / 同为组件 / 同为接口模块 / 同为工具） | 文件整体结构、各部分顺序、导出方式 | 你写出的新文件放进这个目录里，看不出是不同人写的 |
| 2 | 这些文件所在目录的兄弟文件与目录名 | 目录层级约定、文件命名风格（大小写、连字符、后缀） | 命名规则能从现有文件归纳出来，不是你自己定的 |
| 3 | 项目的请求封装文件与一处实际调用点 | 请求发起方式、参数传递、错误处理归属、返回值处理 | 你的请求代码与现有调用点写法一致 |
| 4 | 项目的样式入口、设计变量文件、一个同类页面的样式 | 样式组织方式、变量使用、单位与适配方案、类名规范 | 用变量而不是硬编码值；类名规则与现有一致 |
| 5 | 若有类型定义：项目的类型定义组织方式 | 类型放在哪、命名风格、导出方式 | 类型文件位置与命名与现有一致 |
| 6 | 若涉及登录/权限/埋点：对应能力的封装与一处调用点 | 调用方式、参数、时机 | 通过既有封装调用，不绕过 |
| 7 | 若有测试：同类功能的现有测试文件 | 测试文件位置、命名、组织方式、断言风格 | 新测试与现有测试形态一致 |
| 8 | 项目规范文件与格式化配置 | 缩进、引号、分号、注释密度、语言（注释用中文还是英文） | 改动通过项目 lint 与格式检查 |

**注释密度的对齐：** 项目注释很少时不要写大段注释，项目每个函数都有说明时也要跟上。注释语言跟随项目现状。

**不确定时的处理：** 现有同类文件之间写法不一致（说明项目有历史演进）时，以**最近修改的文件**为准，并在 `delivery.md` 说明你参照了哪一种。差异较大且影响可维护性时询问开发。

### 不做的事

| 禁止 | 原因 | 正确做法 |
| --- | --- | --- |
| 顺手重构无关代码 | 扩大 diff，增加回归风险，超出批准范围 | 记入 `delivery.md` 遗留建议 |
| 为单次需求提前建立未经要求的抽象 | 单一使用场景的抽象是负债，不是资产 | 先直接实现；出现第二个使用场景再考虑抽象 |
| 修改与本次无关的格式与注释 | 让 review 无法聚焦真正的改动 | 只改功能必需的行 |
| 触碰"不允许修改的范围" | 可能覆盖开发未提交的工作 | 需要改时暂停询问 |
| 引入计划外的依赖 | 超出批准范围 | 暂停询问 |

**判断标准：** 每一行改动都能追溯到 `plan.md` 的某个任务。追溯不到就不该改。

## 第二部分：复用优先级

### 优先级顺序

**直接复用 > 修改后复用 > 新增。**

| 优先级 | 什么时候选 | 代价 |
| --- | --- | --- |
| 直接复用 | 现有实现满足需求，无需改动 | 最低。无回归风险 |
| 修改后复用 | 现有实现方向正确，需要扩展 | 中等。有回归风险，需要确认调用方 |
| 新增 | 无可用基础，或改造会污染现有能力 | 最高。增加代码量与维护面 |

**不要为了"看起来更整洁"而放弃复用。** 复用现有组件即使需要传几个参数，也优于新写一个"更干净"的组件。

### 直接复用的确认步骤

1. 读它的实现，确认输入输出、状态、交互满足需求。
2. 读一处现有调用点，确认调用方式与你的用法一致。
3. 确认它没有隐含的前置条件（依赖某个全局状态、依赖某个初始化步骤）。

三步都通过才是真的可直接复用。只看名字或只看签名就调用，常见后果是运行时才发现缺前置条件。

### 修改公共能力前的检查清单

修改被多处使用的代码（请求封装、登录、权限、埋点、公共组件、公共工具）前，必须逐项确认：

| # | 检查项 | 怎么做 | 不通过时 |
| --- | --- | --- | --- |
| 1 | 谁在用？ | 搜出全部调用方并列出清单 | 调用方超出预期范围时重新评估 |
| 2 | 改动向后兼容吗？ | 逐个判断现有调用方在不改代码的情况下行为是否不变 | 不兼容 → 暂停询问开发 |
| 3 | 有隐式依赖吗？ | 检查是否有代码依赖它当前的返回值形状、副作用或调用时序 | 存在隐式依赖 → 暂停询问 |
| 4 | 计划里批准了这个修改吗？ | 对照 `plan.md`"需要修改的文件" | 计划外 → 暂停询问 |
| 5 | 回归范围有多大？ | 调用方清单就是回归范围，写入验证方案 | 回归范围超出可验证能力 → 暂停询问 |

**向后兼容的判断：**

| 改动类型 | 是否兼容 |
| --- | --- |
| 新增可选参数，不传时行为与之前完全一致 | 兼容 |
| 新增一个独立的导出，不改动现有导出 | 兼容 |
| 修改必填参数、参数顺序、参数含义 | **不兼容** |
| 修改返回值结构或字段含义 | **不兼容** |
| 修改默认行为（即使调用方不传参数） | **不兼容** |
| 修改错误抛出方式或错误类型 | **不兼容** |
| 收紧原有的输入校验 | **不兼容**（原本能通过的输入可能被拒绝） |

不兼容的改动一律暂停询问，并提供备选方案："改公共能力（影响 N 处，需回归）"或"本次单独实现（有重复代码，无回归风险）"。

### 新增的前提

选择新增之前，必须能说清"搜过什么、为什么不能复用"。这句话要写进 `delivery.md`，因为它是开发 review 时最常质疑的点。

新增时：位置、命名、结构都按第一部分的对齐清单执行，不自创约定。

## 第三部分：Mock 策略

### 何时用 Mock

| 情形 | 用 Mock | 说明 |
| --- | --- | --- |
| 接口契约未确认 | 是 | 但 Mock 不解除 `missing_api_contract` 阻塞 |
| 契约已确认但后端未就绪 | 是 | 按已确认契约构造 Mock，联调时切换 |
| 需要覆盖异常状态 | 是 | 失败、超时、空数据在真实环境难以稳定触发 |
| 需要覆盖边界数据 | 是 | 超长文本、极值、特殊字符 |
| 契约已确认且后端就绪 | 否 | 直接对接真实接口 |

**前置条件：** 使用 Mock 必须在 `plan.md` 中已批准。计划里没写 Mock 而实现时自行加 Mock，属于扩大范围。

### Mock 数据要覆盖的状态

| 状态 | Mock 要构造什么 | 用于验证 |
| --- | --- | --- |
| 正常 | 典型数据，字段齐全，数量适中 | 主流程渲染 |
| 加载 | 延迟响应 | 加载态展示、加载期间的交互禁用 |
| 空数据 | 空列表 / 空对象（**注意区分"空列表"和"字段缺失"**） | 空态展示 |
| 失败 | 各类失败：网络错误、超时、服务端错误、业务错误码 | 失败态与错误提示分支 |
| 边界值 | 超长文本、字段为空值、数值极值、特殊字符、数量刚好等于分页大小 | 布局不破、不报错 |

**容易漏的两种：**

1. **字段存在但为空** 与 **字段不存在**：两种情况的代码路径不同，都要构造。
2. **部分成功**：列表里某几条数据字段缺失，其余正常。真实环境常见，Mock 里常被忽略。

### Mock 与真实接口切换的注意点

| 注意点 | 说明 |
| --- | --- |
| 切换方式沿用项目现有机制 | 先看项目怎么开关 Mock（环境变量 / 配置项 / 请求拦截 / 开发服务器代理），沿用它，不自建一套 |
| 切换点集中 | Mock 与真实接口的分叉点只在数据层，业务代码不感知 |
| 不留下硬编码分支 | 不在业务代码里写"如果是开发环境就用假数据"这类分支 |
| 提交前确认默认走真实接口 | Mock 开关的默认值必须是关闭。默认开着的 Mock 会导致联调时数据不对却查不出原因 |
| Mock 数据不含真实数据 | 不使用真实用户信息、真实业务数据、真实凭证 |
| 交付时说明 Mock 状态 | `delivery.md` 写清哪些接口仍是 Mock、切换开关在哪、切换后需要重新验证什么 |

### Mock 不能掩盖契约缺失

**这是最容易出错的一点。** Mock 让功能"看起来能跑"，但契约仍然是虚构的。

| 必须做 | 不能做 |
| --- | --- |
| 契约缺失时保留 `missing_api_contract` 阻塞项（scope 为对应接口任务） | 因为 Mock 跑通了就移除阻塞项 |
| 在 `delivery.md` 明确标注该接口未联调 | 在交付总结里写"接口已完成" |
| 把待确认的契约问题保留在 `context.md` 开放问题 | 把 Mock 里编的字段名当成契约写进 `plan.md` |
| Mock 结构基于已确认部分；未确认部分标注为假设 | 让 Mock 的字段名成为事实标准 |

**判断技巧：** 问自己"如果后端明天给出的契约与我的 Mock 完全不同，需要改多少代码？"——如果答案是"很多"，说明 Mock 的结构已经渗透进业务代码，应该在数据层加一层转换隔离。

## 第四部分：接口对接

### 对接前要核对的九项

契约明确时，对接前逐项核对。**任何一项无法从已确认的契约中得到答案，就是契约不完整。**

| # | 核对项 | 要确认到什么程度 | 缺失的后果 |
| --- | --- | --- | --- |
| 1 | 请求方法、路径、参数 | 方法确定；路径确定（含路径参数位置）；每个参数的名称、类型、是否必填、默认值 | 请求发不出去或参数被忽略 |
| 2 | 响应结构、字段类型 | 每个字段的名称、类型、是否可空、嵌套层级；列表的包装结构 | 渲染时取不到值或类型错误 |
| 3 | 业务错误码 | 错误码清单、每个码的含义、对应的用户提示、是否需要特殊处理（如跳登录） | 失败时只能给一句通用提示，用户不知道该做什么 |
| 4 | 鉴权方式 | 凭证放在哪（请求头 / 参数）、是否需要额外的权限参数、失效时的响应特征与处理 | 请求被拒绝，或失效后陷入死循环 |
| 5 | 防重与幂等 | 重复请求由哪一端保证幂等；前端是否需要请求锁或幂等键；重复提交的响应是什么 | 用户连点导致重复数据 |
| 6 | 加载与空状态 | 什么响应算"空"（空列表 / 空对象 / 特定标记）；加载期间是否允许其他操作 | 空态与失败态混淆 |
| 7 | 超时 | 超时时长（用项目统一配置还是单独设置）；超时后是否重试、重试几次 | 慢接口下页面无限加载 |
| 8 | 敏感字段 | 哪些字段敏感；是否可落地存储；是否可进埋点；展示时是否需要脱敏 | 合规问题，事后无法补救 |
| 9 | 分页与排序 | 分页参数形式、总数字段、是否有游标；排序参数与默认排序 | 分页错乱或数据重复 |

第 3、5、8 项最常被跳过，也最容易造成线上问题。契约里没有错误码清单时，不要自己按数字规律推测含义。

### 对接的执行要点

1. **通过项目现有请求封装发起请求**，不绕过封装直接用底层 HTTP 能力。
2. **错误处理归属遵循项目约定**：先确认统一拦截器已经处理了什么（登录失效、通用错误提示），只补充它没处理的业务分支，不重复处理。
3. **响应到视图之间加一层转换**：接口字段直接铺满模板会导致契约变化时改动面很大。转换层的存在形式沿用项目约定。
4. **不在业务代码里兼容多种响应结构**（见下文冲突处理）。

### 接口文档与实际响应不一致时

这是阶段三最常见的阻塞来源，处理流程固定。

**处理步骤：**

| # | 动作 | 细节 |
| --- | --- | --- |
| 1 | 停止受影响的接口任务 | 只停这个接口相关的任务及其下游，不停整个实现阶段 |
| 2 | 记 `api_conflict` 阻塞项 | scope 为对应接口（如 `<项目名>/<接口标识>`），details 说明冲突内容，不含凭证 |
| 3 | 把冲突写入 `context.md` 开放问题 | 完整记录文档说法、实际响应、差异点 |
| 4 | 询问开发或后端 | 遵守"一次只提一个关键问题" |
| 5 | 无依赖的任务继续 | 不因为一个接口冲突而停下全部工作 |
| 6 | 确认后追加 `decisions.md` 并更新 `plan.md` | 可执行内容变化时更新 `planVersion` 并重新批准 |

**绝对不做：自行兼容两套含义。**

反例形态：写一段代码同时处理"文档里的字段"和"实际返回的字段"，哪个有值用哪个。

为什么不行：

1. 两套字段可能语义不同（例如同名字段一边是分，一边是元），"哪个有值用哪个"会产出错误结果。
2. 掩盖了真正的问题：要么文档过期，要么后端有 bug，要么环境不对。兼容代码让这个问题永久留在代码里。
3. 后续维护者无法判断哪套是正确的，兼容分支永远删不掉。

**例外：** 后端明确确认"两种结构在不同版本并存，前端需要同时支持"，并写入 `decisions.md` 后，才可以实现兼容。这时兼容是已确认的需求，不是自行猜测。

### 询问时要给出的信息

模糊的提问（"接口对不上"）无法推进。必须给出四项：

```markdown
### 开放问题 OQ-01：<接口标识> 响应结构与文档不一致

**文档契约：**
- 来源：<接口文档的哪一节 / 谁在什么时候确认的>
- 说法：<文档里字段的名称、类型、含义，按文档原文>

**实际响应：**
- 环境：<测试环境 / 联调环境>
- 观测时间：<时间>
- 实际结构：<实际返回的字段名称、类型、层级，不含真实业务数据与凭证>

**差异点：**
1. <字段 A：文档为类型 X，实际为类型 Y>
2. <字段 B：文档中存在，实际缺失>
3. <字段 C：名称相同但含义可能不同（文档说明 vs 实际数值特征）>

**影响：**
- 阻塞任务：<任务 ID>
- 影响功能：<具体功能>
- 是否影响其他任务：<是/否，说明>

**可选处理方案：**
- A 前端按实际响应适配（快，但如果后端后续修正则需再改一次）
- B 要求后端按文档修正响应（前端不改，等待后端）
- C 文档过期，更新文档后前端按新文档实现（需后端确认新文档为准）

**建议：** <你的建议及理由>
```

**记录实际响应时的注意：** 只记结构（字段名、类型、层级），不粘贴真实业务数据，不记录任何凭证或 Token。

## 第五部分：实现中必须暂停的情形

| # | 情形 | 触发特征 | 阻塞项 |
| --- | --- | --- | --- |
| 1 | UI 缺失 | 实现到某个状态时发现没有对应设计（常见于加载、空、失败态） | `missing_ui`，scope 为页面或任务 |
| 2 | 契约不符 | 接口文档与实际响应不一致 | `api_conflict`，scope 为接口 |
| 3 | 契约缺失 | 需要对接真实接口但无已确认契约 | `missing_api_contract`，scope 为接口任务 |
| 4 | 公共能力影响 | 需要做不向后兼容的公共能力修改 | 视情况；影响范围写入开放问题 |
| 5 | 与开发未提交修改冲突 | 要改的文件在"不允许修改的范围"内，或工作区有未提交改动 | 不记阻塞码，直接询问 |
| 6 | 需要扩大范围 | 发现必须改计划外的文件才能完成任务 | 不记阻塞码，直接询问 |
| 7 | 需要新增依赖 | 实现中发现缺少某项能力 | 不记阻塞码，直接询问 |

### 暂停后的四个动作

固定顺序，不能省略任何一步：

| # | 动作 | 要点 |
| --- | --- | --- |
| 1 | 记范围级阻塞项 | scope 精确到项目/模块/任务/接口。**不要用整个需求或整个阶段作为 scope** |
| 2 | 写 `context.md` 开放问题 | 记录未确认事实、影响范围、建议选项（互斥的 A/B/C）。事实、推断、假设分开标注 |
| 3 | 询问开发 | 一次只提一个关键技术问题，其余排队 |
| 4 | 确认后追加 `decisions.md` 并更新 `plan.md` | 只有已确认的结论进 `decisions.md`；计划的可执行内容变化时更新 `planVersion` 并重新批准 |

### 暂停期间做什么

**继续执行不依赖被阻塞范围的任务。** 判断依据是 `plan.md`"技术任务及依赖"的依赖链。

| 情况 | 处理 |
| --- | --- |
| 有无依赖的任务可做 | 继续做，全局 `status` 保持 `active` |
| 全部剩余任务都依赖被阻塞范围 | 全局 `status` 为 `blocked` |
| 不确定某任务是否受影响 | 按受影响处理（保守），并在开放问题里说明 |

**不要做的事：** 为了"不闲着"去做计划外的工作，或者基于假设先把被阻塞的部分实现出来"等确认了再调整"。后者会让假设固化成既成事实。

### 临时假设的边界

开发要求"先按临时方案做"时，遵守这些边界（详见 SKILL.md）：

| 内容类型 | 是否允许基于临时假设开发 |
| --- | --- |
| 涉及安全、资金、权限、隐私、数据写入的 P0 内容 | **不允许**，等正式确认 |
| 其他内容 | 只有开发明确授权后可继续，授权本身记入 `context.md` |

临时实现必须可回退，在 `context.md` 记录改动范围与回退方式。任何临时实现都不得交付或部署。超过一个工作日未确认时暂停相关实现。

## 常见误判纠正

### 误判 1：按框架的一般写法直接开写

不对：知道项目用了某个框架，就按对该框架的一般认知写新文件。

正确：先读 2-3 个项目里最同类的现有文件，对齐结构、命名、请求方式、样式组织。同一个框架在不同项目里的组织方式差别可能很大。

### 误判 2：为纯逻辑需求创建页面结构

不对：需求是修正一个计算逻辑，却按"标准流程"新建了页面文件和组件文件。

正确：逻辑、接口、埋点、Bug 修复类需求直接执行对应任务，第 2 步跳过。

### 误判 3：Mock 跑通就认为接口完成

不对：Mock 数据能正常渲染，于是移除 `missing_api_contract`，在交付总结写"接口已对接"。

正确：Mock 不解除契约缺失阻塞。`delivery.md` 必须明确写"该接口仍为 Mock，未联调，切换开关在 X，切换后需重新验证 Y"。

### 误判 4：接口对不上就写兼容代码

不对：文档说字段 A，实际返回字段 B，于是写"A 有值用 A，否则用 B"。

正确：停止该接口任务，记 `api_conflict`，询问。两套字段的语义可能不同，兼容会产出错误结果，并且这段代码永远删不掉。

### 误判 5：把整个实现阶段标为阻塞

不对：一个接口冲突，把 `stageStatus.implementation` 设为 `blocked`。

正确：阻塞项的 scope 是具体接口。其他无依赖任务继续，全局 `status` 保持 `active`。只有全部剩余任务都无法推进时才 `blocked`。

### 误判 6：顺手重构或清理无关代码

不对：实现过程中看到旁边的代码写得不好，一起改了；看到未使用的旧函数，删了。

正确：只改能追溯到 `plan.md` 任务的行。观察到的问题写进 `delivery.md` 遗留建议。只删除"本次修改造成的"无效代码。

### 误判 7：为单次需求提前抽象

不对：只有一个页面用到的逻辑，先抽成一个通用工具函数并加配置项，"以后可能会用到"。

正确：直接实现。出现第二个使用场景时再抽象。单一使用场景的抽象增加理解成本，且抽象方向往往在第二个场景出现时才明确。

### 误判 8：基于未确认的假设先实现

不对：某个交互规则还没确认，先按自己认为合理的方式实现，"等确认了再改"。

正确：暂停该范围，做无依赖的任务。已经写出来的实现会被当成既成事实，确认时对方容易顺着你的实现回答，而不是给出真实需求。

### 误判 9：在业务代码里直接使用接口字段

不对：接口响应对象直接传进渲染层，模板里逐个取原始字段。

正确：在数据层做一次转换。契约变化时只改转换层，业务代码不动。这在契约尚未完全稳定时尤其重要。

### 误判 10：暂停时 scope 写得太粗

不对：`{"code": "api_conflict", "scope": "<需求标识>"}`。

正确：`scope` 精确到接口或任务（如 `<项目名>/<接口标识>`）。scope 太粗会让本可继续的任务全部停摆，也让恢复时无法判断该重做什么。

## 总结

**实现顺序：**
1. 按 `plan.md` 任务依赖执行，跳过不适用的步骤
2. 非页面类需求不强制创建页面结构
3. 只实现已确认的加载、失败、防重复、权限、平台差异
4. 清理只清本次造成的无效代码，既有死代码报告不删

**风格对齐：**
1. 动手前读同类现有文件，对齐八项（结构、命名、请求、样式、类型、公共能力调用、测试、规范）
2. 现有写法不一致时以最近修改的为准并说明
3. 每一行改动都能追溯到计划任务

**复用：**
1. 直接复用 > 修改后复用 > 新增
2. 直接复用要读实现和一处调用点，确认无隐含前置条件
3. 修改公共能力前过五项检查；不向后兼容一律暂停
4. 选择新增要能说清"搜过什么、为什么不能复用"

**Mock：**
1. 用于契约未确认、后端未就绪、覆盖异常与边界
2. 覆盖正常、加载、空、失败、边界五类；注意"字段为空"与"字段缺失"的区别
3. 切换机制沿用项目现有方式，默认走真实接口
4. Mock 不解除 `missing_api_contract`，交付时如实标注未联调

**接口对接：**
1. 对接前核对九项；任一项无答案就是契约不完整
2. 通过项目现有封装发起请求，响应到视图之间加转换层
3. 文档与实际不一致：停该接口 → 记 `api_conflict` → 写开放问题 → 询问 → 无依赖任务继续
4. 绝不自行兼容两套含义，除非后端确认并入 `decisions.md`
5. 提问必须给出文档契约、实际响应、差异点、A/B/C 处理方案

**暂停：**
1. 七种情形必须暂停
2. 四个动作：记范围级阻塞 → 写开放问题 → 询问（一次一个）→ 确认后追加决策并更新计划
3. 暂停期间做无依赖任务，不做计划外工作，不基于假设先实现

**判断技巧：**
- 问自己"这行改动对应计划里的哪个任务？"→ 说不出就不该改
- 问自己"这个字段名是谁确认的？"→ 说不出就不能依赖它
- 问自己"改这个公共文件后，现有调用方不改代码还能正常工作吗？"→ 不能就暂停
- 问自己"如果契约明天完全变了，要改多少代码？"→ 很多就说明缺转换层
- 问自己"我是在实现已确认的结论，还是在替别人做决定？"→ 后者立即暂停
